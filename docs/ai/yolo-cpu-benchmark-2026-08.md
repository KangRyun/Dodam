# YOLO CPU 추론 성능 실측 (2026-08-02)

> Jira: `S15P11B209-609` · 측정: 이강륜
> 결론을 인용하는 곳: `infra/k8s/base/ai.yaml` resources · 추론 가속 논의(양자화·CPU 상한)

## 0. 무엇을 측정했나

운영 EC2(CPU 4코어, 15GiB)에서 그림 분석 YOLO 추론의 **레이턴시 p50/p95 · 메모리 피크**를
운영과 동일한 조건으로 실측했다. 용량 산정·리소스 설정·가속 투자 판단의 근거 수치다.

**운영 파드를 건드리지 않았다** — k8s 리소스 limits 의 실체는 커널 cgroup 이므로,
같은 이미지·같은 가중치·같은 cgroup 제한의 **별도 docker 컨테이너**에서 측정하면
수치가 그대로 이식된다(같은 커널). 네트워크 차단(`--network=none`)·가중치 읽기 전용
마운트·실아동 그림 미사용(합성 스케치 생성) 조건.

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| 이미지 | `127.0.0.1:5000/dodam-ai:d47c3e1a` (당시 운영 배포본) |
| 가중치 | ai-models PVC 실물 (`htp_best.pt`·`sketch_base.pt`, sha256 검증 통과) |
| 런타임 | **PyTorch(.pt) CPU** — ONNX 아님 (torch 스레드 4 = 보이는 코어 수) |

| 반복 | 워밍업 3회 + 본측정 25회 (케이스×모델×CPU 조건별) |
| 측정 경로 | `yolo_client.detect_and_annotate` 전체(EXIF 확인+추론+후처리+주석 PNG 인코딩) |
| 스크립트 | `infra/scripts/ai-inference-bench.py` (재현 명령은 스크립트 머리말) |

## 2. 결과 — 레이턴시 (전체 경로, ms)

| 케이스 | CPU 1 (운영 현재) p50 / p95 | CPU 2 p50 / p95 | 배속 |
|---|---|---|---|
| HTP · 캔버스 1080² | 1,515 / 1,717 | 788 / 838 | **1.9×** |
| sketch · 캔버스 1080² | 1,535 / 1,711 | 623 / 685 | **2.5×** |
| HTP · 사진 3024×4032 | 1,658 / 1,897 | 1,056 / 1,105 | 1.6× |
| sketch · 사진 3024×4032 | 1,591 / 1,701 | 905 / 989 | 1.8× |

- ultralytics 자체 분해(p50): **추론(conv 연산)이 ~90%**, 전처리 6~9ms, 후처리 ~1ms.
  전체 경로 − predict ≈ 120ms(주석 PNG 인코딩 등). → **병목은 순수 행렬 연산**이라
  CPU 배정이 거의 그대로 배속으로 환산된다.
- 첫 호출(콜드)은 1.5~4.9초 — 프로세스당 1회. 기동 시 워밍업 1회로 흡수 가능.
- p95 가 p50 대비 +10% 안쪽 — 단독 실행 시 지터는 작다.
- 모델 로드(sha256 검증 포함): htp 1.6s · sketch 0.3s. torch+ultralytics import 4.5s.

**환산**: HTP 최종분석은 그림 3장(집·나무·사람) → YOLO 구간만
CPU 1 에서 ~4.5s, CPU 2 에서 ~2.4s. 여기에 VLM/LLM(GMS) 호출이 더해진다.

## 3. 결과 — 메모리 (⚠️ 출시 블로커였음)

| 조건 | cgroup 피크 |
|---|---|
| CPU 1, 두 모델 로드 + 960 추론 | **1,748 MiB** |
| CPU 2, 동일 | 1,527 MiB |
| **--memory=1g (운영 상한과 동일) 재현 실험** | **첫 htp 추론 중 OOM 즉사(137)** |

- 운영 ai 파드의 당시 상한 1Gi 는 **실분석 1건을 못 버티는 값**이었다.
  파드가 살아 있던 이유: 배포 후 분석 요청이 0건이었기 때문(로그 확인).
- 이력 맥락: 2026-07-30 512Mi→1Gi 상향은 sketch imgsz 640 시절 트래픽 기준이다.
  이후 v4 대비로 SKETCH_IMGSZ 가 960 이 되며(761) 활성화 메모리가 (960/640)²≈2.25배
  급증했다 — 1Gi 가 지나간 트래픽에서 버텼다는 사실이 현재 안전을 보장하지 않았다.
- ai.yaml 의 이전 근거 주석("실측 77MB")은 YOLO 없이 잰 값 — 이 문서로 대체한다.

## 4. 리소스 설정 결론 (`infra/k8s/base/ai.yaml`)

```yaml
resources:
  requests: { memory: 512Mi, cpu: 200m }
  limits:   { memory: 2Gi,   cpu: "2" }
```

- **memory limit 2Gi**: 실측 피크 1.75Gi + 여유 ~15%. 호스트 15GiB 단일 노드에서
  limit 은 예약이 아니므로(초과 시에만 킬) 안전.
- **cpu limit 2**: 실측 1.6~2.5× 개선. 호스트 4코어 — limit 은 상한일 뿐 점유 예약이
  아니고, 분석은 간헐 버스트라 상시 경합 없음.
- requests 512Mi: 두 모델 상주 후 정상 상태(~660MiB 관측)에 가깝게 — 스케줄러 힌트.

## 5. 남은 판단 재료 (후속)

- **전체 파이프라인에서 YOLO 비중**: 분석 1건 = 다운로드+YOLO+VLM/LLM(GMS).
  GMS 왕복이 수 초면 YOLO 최적화의 체감 상한이 낮다 — 실트래픽 후 스팬 확인.
- **양자화(INT8)**: 운영이 .pt(PyTorch)이므로 ONNX 내보내기부터 필요. CPU 2 상향으로
  0.6~1.1s 가 되면 양자화 투자(정확도 검증 비용) 대비 이득을 다시 판단.
- **k6 부하테스트에 AI 경로 없음**: 현행 k6 는 `/ai/health` 만 친다. 추론 동시성
  (uvicorn 단일 워커에서 요청 대기열) 거동은 별도 측정 필요.
