## 1. 배포 후 검증 절차

순서대로 확인한다. 각 단계는 "아래 단계의 전제"다 — 컨테이너가 죽었는데 e2e를 먼저 볼 이유가 없다.

### 1-1. 컨테이너 상태

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

**정상 기대값:**

| 컨테이너 | 기대 Status | 비고 |
|---|---|---|
| dodam-mysql | `Up ... (healthy)` | |
| dodam-redis | `Up ... (healthy)` | |
| dodam-backend | `Up ... (healthy)` | ⚠️ healthy = "8080 리슨 중"일 뿐(TCP 체크). 기능 정상은 1-3에서 확인 |
| dodam-ai | `Up ... (healthy)` | `/health` HTTP 체크 |
| dodam-nginx | `Up ...` | **healthcheck 미설정 — `(healthy)`가 안 붙는 게 정상.** 라우팅은 1-3에서 검증 |
| dodam-certbot | `Up ...` | 갱신 루프만 도는 컨테이너 — healthcheck 없음 |
| dodam-jenkins | `Up ...` | 별도 compose(dodam-cicd). 앱 장애와 무관 |

- `Restarting (1) x seconds ago` 반복 = 크래시 루프 → `docker logs --tail 100 dodam-backend` 로 원인부터. Flyway 오류인지 env 오류인지가 3절 판단을 가른다.
- `(unhealthy)` = 떠는 있는데 체크 실패 → 1-2로.

### 1-2. healthcheck 상세

```bash
# 상태 한 줄씩
for c in dodam-mysql dodam-redis dodam-backend dodam-ai; do
  echo "$c: $(docker inspect -f '{{.State.Health.Status}}' $c)"
done

# unhealthy인 컨테이너의 최근 체크 로그(왜 실패했는지 원문 확인)
docker inspect -f '{{json .State.Health.Log}}' dodam-backend | python3 -m json.tool
```

- 파이프라인의 Healthcheck 스테이지도 같은 값을 본다(mysql·backend·ai가 healthy 될 때까지 대기). 여기서 healthy면 파이프라인 기준은 통과한 것.
- ⚠️ 함정: **컨테이너를 재생성하지 않으면 healthcheck 정의는 옛날 것이 남는다.** compose 파일의 healthcheck를 고쳐도 `up -d`로 컨테이너가 재생성돼야 반영된다. "코드는 고쳤는데 계속 unhealthy"면 `docker inspect -f '{{.Config.Healthcheck.Test}}' <컨테이너>` 로 실제 실행 중인 체크 명령이 최신인지 대조할 것(2026-07-23 dodam-jenkins에서 실제 발생 — 구 경로 `/login` 체크가 남아 만성 unhealthy, 서비스 자체는 정상이었다).

### 1-2b. AI 연동 모드 — "healthy인데 결과가 가짜" 판별 (S15P11B209-722)

```bash
# ① BE가 실제 AI를 호출하는지 (셋 다 http 여야 한다)
docker compose exec backend env | grep -E "AI_DRAWING_ANALYSIS_MODE|AI_OBSERVATION_MODE|AI_TTS_MODE"

# ② 부팅 로그의 모드 한 줄 — mock 이 섞이면 WARN 으로 남는다
docker logs dodam-backend 2>&1 | grep "AI 연동 모드"

# ③ AI 서버의 모델 준비 상태 (objectDetection=READY 여야 탐지가 돈다. curl 미설치라 python 사용)
docker compose exec -T ai python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/internal/v1/health').read().decode())" | python3 -m json.tool
```

- **기본값은 `http`다.** 값이 비어 있어도 실제 AI를 호출한다. `mock`으로 보이면 누군가 명시적으로 지정했거나 `SPRING_PROFILES_ACTIVE=local`이 켜진 것이다.
- ⚠️ 실제 사고(2026-07-29): `AI_DRAWING_ANALYSIS_MODE=mock` + `AI_TTS_MODE` 미설정 상태로 운영이 돌았다. 컨테이너는 전부 healthy였고 리포트도 생성됐지만, **탐지가 가짜여서 관찰 리포트의 근거가 아이 그림과 무관**했다. healthcheck로는 절대 잡히지 않는 유형이라 이 절을 따로 둔다.
- ③에서 `objectDetection=NOT_READY`면 가중치 부재·checksum 불일치다. 경로 2종(`YOLO_MODEL_PATH`·`SKETCH_MODEL_PATH`)이 모두 주입됐는지 확인할 것(S15P11B209-721).

### 1-3. 게이트웨이 e2e — 외부 진입 경로 실검증 (★401 해석 주의)

컨테이너 health만으론 nginx 라우팅 고장(빈 conf 등)을 못 잡는다(2026-07-22 사고). 실제 외부 경로로 찔러본다.
**2026-07-22 밤 백엔드 309 머지 이후 `/api/v1/**`는 (OAuth 로그인·reissue·OPTIONS 제외) 전부 Bearer Token 필수다. 따라서 미인증 curl의 `401`은 장애가 아니라 "백엔드가 살아서 인증 필터가 일하고 있다"는 정상 신호다.**

```bash
# 상태코드만 뽑는 공통 함수 느낌으로 — 어디서든(로컬 PC 포함) 실행 가능
curl -sS -o /dev/null -w '%{http_code}\n' https://i15b209.p.ssafy.io/ai/health
```

**프로브별 정상 기대값 표:**

| # | 프로브 (전부 `https://i15b209.p.ssafy.io` 기준) | 정상 기대값 | 이 값이 아니면 |
|---|---|---|---|
| 1 | `GET /ai/health` | **200** `{"status":"ok"}` | 502/504 = nginx→ai 라우팅 또는 ai 다운 |
| 2 | `GET /api/v1/ping` (미인증 — 존재하지 않는 경로여도 됨) | **401** `AUTH_401_006` | 502 = backend 다운/라우팅 고장 · 200 = 인증 필터 미작동(그게 더 큰 사고) |
| 3 | `GET /api/v1/ping` + `-H 'Authorization: Bearer dummy'` | **401** `AUTH_401_002` | **503 `AUTH_503_001` = JWT 시크릿 누락 → 1-4로 직행** |
| 4 | `POST /api/v1/auth/oauth/kakao` (빈 body) | **400** `COMMON_400_003` | 공개(인증 제외) 엔드포인트 생존 확인 — 401이 나오면 필터 제외 목록이 깨진 것 |
| 5 | `POST /api/v1/auth/reissue` (빈 body) | **400** | 위와 동일한 공개 경로 생존 확인 |
| 6 | `GET /` | **200** (준비중/프론트 페이지) | 정적 서빙 확인 |
| 7 | `GET http://i15b209.p.ssafy.io/` (http) | **301** → https | 80 리다이렉트 확인 |

- #2가 401인 이유: 인증 필터가 `/api/v1/*` 전체에 컨트롤러보다 먼저 걸려 있어, **없는 경로조차 401을 먼저 반환**한다. 즉 401 하나로 "nginx 라우팅 + backend 기동 + 필터 동작" 세 가지가 한 번에 검증된다.
- #3는 정상/시크릿누락을 가르는 판별 프로브다. dummy 토큰을 실제로 해석하려는 순간에만 JWT 설정 검증이 일어나기 때문(1-4 참조).
- 서버 안(nginx 컨테이너)에서 확인할 때는 **반드시 `127.0.0.1`** — 컨테이너 안 `localhost`는 IPv6(::1)로 먼저 풀리는데 nginx는 IPv4만 리슨해 항상 refused가 난다(오탐 2회 이력). 파이프라인 Healthcheck 스테이지의 e2e도 같은 이유로 `https://127.0.0.1/ai/health`를 친다.

```bash
# 서버 내부에서 게이트웨이 통과 확인(파이프라인과 동일한 방식)
docker exec dodam-nginx wget --no-check-certificate -q -O - -T 5 https://127.0.0.1/ai/health
```

### 1-4. 시크릿 누락형 장애 판별 — "healthy인데 로그인만 503"

**원리(왜 healthcheck가 못 잡나):** backend는 `JWT_SECRET`이 비어 있어도 정상 부팅한다(`application.yml`이 기본값 빈 문자열 허용). 검증은 **토큰을 발급/해석하는 순간**에 일어나 — 시크릿이 공백이거나 32바이트 미만이면 그 요청만 `503 AUTH_503_001`("인증 서비스 설정이 완료되지 않았습니다")로 fail-closed 된다. 컨테이너 healthcheck는 TCP 8080 리슨만 보므로 **healthy인데 인증 API만 전멸**하는 상태가 성립한다.

**판별:**

```bash
# ① 1-3 표의 #3 프로브: Bearer dummy → 401이면 시크릿 정상, 503 AUTH_503_001이면 누락
curl -sS -H 'Authorization: Bearer dummy' https://i15b209.p.ssafy.io/api/v1/ping
# ② 컨테이너에 변수가 실제로 들어갔는지(값 말고 "존재"만 — 값을 화면에 출력하지 않는다)
docker exec dodam-backend sh -c 'test -n "$JWT_SECRET" && echo "JWT_SECRET: 있음(길이 $(printf %s "$JWT_SECRET" | wc -c)바이트)" || echo "JWT_SECRET: 없음"'
```

**503 코드 구분 (둘 다 "healthy인데 인증만 죽는" 모양새라 혼동 주의):**

| 응답 코드 | 의미 | 조치 |
|---|---|---|
| `AUTH_503_001` | JWT/OAuth 필수 설정 누락·불량(시크릿 32바이트 미만 포함) | Jenkins Credentials의 `dodam-env`(Secret file) 수정 → develop 재빌드로 재배포. **롤백 아님** — 구버전을 띄워도 시크릿이 없긴 마찬가지다. ⚠️ **전제**: compose `backend.environment`에 해당 변수 전달 항목이 있어야 credential 값이 컨테이너에 도달한다(`--env-file`은 `${...}` 보간 전용). 2026-07-23 기준 JWT/OAuth 변수는 미배선 — `[INFRA] 인증·AI 연동 환경변수 배선` 이슈 완료 전에는 이 조치만으로 해소되지 않음 |
| `AUTH_503_002` | Redis 장애(Refresh 세션 확인 불가) | `docker ps`에서 dodam-redis 상태·로그 확인. 역시 롤백 아님 |

시크릿 수정 시 주의: 배포는 Jenkins Credentials `dodam-env`가 소스다. 서버의 `infra/.env`는 수동 조작(롤백 등)용 사본이므로 **둘을 함께 갱신**해 드리프트를 막는다. 값은 어디에도(채팅·커밋·화면 캡처) 남기지 않는다 — 가드레일.

### 1-5. 옛 코드형 장애 판별 — "healthy인데 최근 수정이 통째로 사라짐" (S15P11B209-771)

**증상:** 파드는 전부 `Running`·`Ready`인데 최근 머지된 기능이 없다. 새로 생긴 경로가 404, 고친 버그가 되살아나 있다. 로그에도 에러가 없다 — **옛 빌드가 정상 동작 중**이기 때문이다.

**원리:** 배포 경로가 둘이고 서로 다른 태그를 쓴다.

| 경로 | 태그 | 언제 |
|---|---|---|
| Jenkins `kubectl set image` | `:{SHA}` | 평소 배포 |
| `kubectl apply -k overlays/prod` | `:prod` | 매니페스트 변경 반영 |

`apply -k`를 돌리면 이미지가 SHA에서 `:prod`로 **되돌아간다.** 이때 파드가 `imagePullPolicy: IfNotPresent`로 뜨면 kubelet이 **노드에 캐시된 옛 `:prod`** 를 재풀 없이 쓴다. 레지스트리의 `:prod`가 최신이어도 소용없다.

> **2026-08-04 실제 사고.** 817(웹 소셜 로그인) 매니페스트 반영으로 `apply -k overlays/prod`를 돌렸다가 web·backend·ai·gateway **네 개가 전부** 옛 빌드로 퇴행했다. `/login` 404, 약 10분. 08-02에도 같은 원인의 2차 퇴행이 있었다.

**판별:** 파드가 실제로 물고 있는 다이제스트를 본다. **레지스트리를 보면 안 된다** — 레지스트리가 최신이어도 노드 캐시는 다를 수 있다.

```bash
# ① 파드가 실제 실행 중인 이미지 다이제스트
kubectl -n dodam get pod -l app=web -o jsonpath='{.items[0].status.containerStatuses[0].imageID}{"\n"}'
# ② 노드에 캐시된 :prod 다이제스트 (①과 달라야 정상 — 같으면 옛것을 물고 있다는 뜻)
sudo k3s crictl images | grep 'dodam-web:prod'
# ③ 지금 배포됐어야 할 커밋
git -C /home/kr/S15P11B209 rev-parse --short origin/develop
```

**복구:** SHA 태그로 되돌린다(Jenkins가 쓰는 것과 같은 방식).

```bash
TAG=$(git -C /home/kr/S15P11B209 rev-parse --short origin/develop)
kubectl -n dodam set image deployment/web     web=127.0.0.1:5000/dodam-web:"$TAG"
kubectl -n dodam set image deployment/backend backend=127.0.0.1:5000/dodam-backend:"$TAG"
kubectl -n dodam set image deployment/ai      ai=127.0.0.1:5000/dodam-ai:"$TAG"
kubectl -n dodam set image deployment/gateway nginx=127.0.0.1:5000/dodam-nginx:"$TAG"
```

`set image`는 env·시크릿 참조를 건드리지 않으므로, `apply -k`로 반영한 매니페스트 변경은 그대로 남는다.

**항구 대책(적용됨):** `base/*.yaml`의 4개 컨테이너에 `imagePullPolicy: Always`를 지정했다. 레지스트리가 루프백(`127.0.0.1:5000`)이라 다이제스트만 확인하고 레이어는 캐시를 재사용하므로 기동이 느려지지 않는다. Jenkins의 `:prod` 갱신은 방어의 나머지 절반이다 — **둘 중 하나만으로는 막히지 않는다.**

## 2. 롤백 절차 — `:SHA` 태그 기반

빌드마다 로컬 레지스트리에 `127.0.0.1:5000/dodam-{backend,ai,nginx,web}:{git 짧은 SHA}` 가 푸시된다(Jenkinsfile Deploy 스테이지의 `push-staging-images.sh`). 이것이 불변 복원지점이고, **롤백 = 그 SHA 태그로 `kubectl set image`** 다.

> ⚠️ **2026-08-04 개정(S15P11B209-791).** 이전 판은 `docker tag …:local` + `docker compose up -d` 였다.
> 그건 컷오버(360) 전 절차이고, **지금 실행하면 안 된다** — compose nginx 가 떠서 k8s gateway 와
> hostPort 80/443 을 다툰다(CNI portmap DNAT 라 깨끗한 에러가 아니라 조용한 이상 동작이 된다).
> `infra/docker-compose.yml` 자체가 791 에서 빌드 전용(`docker-compose.build.yml`)으로 축소돼
> 이제 그 명령은 실행조차 되지 않는다. `:local` 태그도 배포 경로가 아니다 — k8s 는 레지스트리를 본다.

### 2-0. 롤백 전 필수 확인: DB 마이그레이션 (건너뛰면 2차 장애)

backend는 기동 시 Flyway가 마이그레이션을 적용한다(`validate-on-migrate: true`, roll-forward 전략 — 되돌리는 down 스크립트가 없다). **문제의 배포가 새 마이그레이션(V7, V8, …)을 이미 DB에 적용했다면, 구버전 앱은 "자기가 모르는 적용 이력"을 만나 validate 실패로 부팅조차 실패할 수 있다.** 이 경우 이미지 롤백은 답이 아니다 → 2-3(revert MR, roll-forward)으로 간다.

```bash
# ① DB에 적용된 마이그레이션 이력(최근 5건) — 포트 개방 없이 kubectl exec로만(가드레일)
kubectl -n dodam exec -it mysql-0 -- \
  mysql -u root -p -e "SELECT version, description, installed_on FROM b209.flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;"

# ② 문제 커밋 구간에 migration 변경이 있었는지(서버 리포는 GitLab보다 뒤처질 수 있음 — fetch 먼저)
git -C /home/kr/S15P11B209 fetch origin develop
git -C /home/kr/S15P11B209 diff --stat <되돌아갈SHA>..origin/develop -- backend/src/main/resources/db/migration/
```

| ② 결과 | 판단 |
|---|---|
| migration 변경 없음 | 이미지 롤백 안전 → 2-1로 |
| 새 migration 있음 + ①에서 이미 적용됨 | **이미지 롤백 금지** — 2-3 revert MR로 직행. 새 스키마가 구 코드와 호환되는 특수한 경우에만(리뷰 후) 예외 |

### 2-1. 직전 정상 SHA 찾기 (3가지 방법 — 위에서부터 신뢰)

1. **Mattermost 알림(가장 정확):** 마지막으로 `✅ 빌드 성공 … 🚀 서버 배포됨`이 붙은 알림의 ``커밋 `xxxxxxxx` ``가 "배포되고 헬스체크까지 통과한" SHA다.
2. **레지스트리 태그 목록:** 푸시된 SHA 가 곧 후보다.
   ```bash
   curl -s http://127.0.0.1:5000/v2/dodam-backend/tags/list | tr ',' '\n' | tr -d '"[]' | tail -12
   ```
   ⚠️ 함정: 태그가 **있다고 그 빌드가 배포·헬스체크까지 성공했다는 뜻이 아니다**(푸시 직후 rollout 에서
   죽었을 수도). 그래서 MM ✅+🚀 대조가 우선이다. 목록 순서도 푸시 순서가 아니다.
3. **`git log` (fetch 후):** SHA가 어떤 커밋(누구의 어떤 변경)인지 사람 눈으로 확인.
   ```bash
   git -C /home/kr/S15P11B209 fetch origin develop && git -C /home/kr/S15P11B209 log --format='%h %an %s' -8 origin/develop
   ```

지금 떠 있는 게 어떤 SHA인지 모르겠으면 — **파드가 실제로 실행 중인 이미지**를 본다:

```bash
kubectl -n dodam get deploy backend gateway ai web \
  -o custom-columns='DEPLOY:.metadata.name,IMAGE:.spec.template.spec.containers[0].image'
```

> ⚠️ `deploy` 의 `spec` 은 "무엇을 띄우라고 지시했는가"이지 "무엇이 떠 있는가"가 아니다.
> 옛 코드형 장애를 의심 중이라면 **1-5 절**로 갈 것 — 노드 캐시까지 봐야 판별된다(771).

### 2-2. 즉시 지혈 — 서버에서 이미지 되돌리기 (~1분)

```bash
# ⓪ Jenkins에 develop 빌드가 돌고 있는지 먼저 확인 — 돌고 있으면 그 빌드가 곧 되돌린 것을 다시 덮는다.
#    https://i15b209.p.ssafy.io/jenkins/ → dodam-cicd → develop 에서 진행 중 빌드 확인(필요 시 잡 Pause).

# ① 4종 세트를 같은 SHA로 되돌린다 — 반드시 세트로. nginx conf는 이미지에 bake돼 라우팅이
#    백엔드 코드와 함께 진화하므로, 섞어 돌리면 "구 nginx + 신 backend" 같은 미검증 조합이 된다.
#    ⚠️ Deployment 이름과 컨테이너 이름이 다른 것이 있다 — gateway 의 컨테이너는 nginx 다.
SHA=<되돌아갈SHA>   # 예: e5671a22
R=127.0.0.1:5000
kubectl -n dodam set image deployment/backend backend=$R/dodam-backend:$SHA
kubectl -n dodam set image deployment/gateway nginx=$R/dodam-nginx:$SHA
kubectl -n dodam set image deployment/ai      ai=$R/dodam-ai:$SHA
kubectl -n dodam set image deployment/web     web=$R/dodam-web:$SHA

# ② 롤아웃 완료 대기 — web 을 gateway 보다 먼저 확인한다(순서가 어긋나면 `/` 가 잠깐 502).
kubectl -n dodam rollout status deployment/backend --timeout=300s
kubectl -n dodam rollout status deployment/web     --timeout=300s
kubectl -n dodam rollout status deployment/gateway --timeout=300s
kubectl -n dodam rollout status deployment/ai      --timeout=300s

# ③ 검증 — 1절 전체를 다시 통과시킨다(특히 1-3 e2e). 롤백도 배포다.
```

**직전 리비전으로만 되돌리면 되는 경우**는 SHA를 찾을 필요도 없다:

```bash
kubectl -n dodam rollout undo deployment/backend      # 필요한 워크로드마다
kubectl -n dodam rollout history deployment/backend   # 어디로 가는지 먼저 확인
```

- ⚠️ **게이트웨이 재시작은 수 초간 외부 접속을 끊는다** — hostPort + `maxSurge: 0` 구조라 그렇다.
  backend 는 replicas 2 + `maxUnavailable: 0` + preStop 8s 로 무중단이다(362 실증).
- ⚠️ `set image` 로 되돌린 상태는 **`kubectl apply -k overlays/prod` 한 번이면 `:prod` 로 되돌아간다.**
  롤백을 유지해야 하면 그 사이 apply 를 돌리지 말 것. 정상 복귀는 2-3(revert MR)로 한다.
- ⚠️ 설정은 이미지가 아니라 **k8s Secret/ConfigMap** 이 소유한다 — 이미지를 되돌려도 시크릿은 그대로다.
  `JWT_SECRET` 류 문제라면 롤백이 아니라 1-4 절차다.
- ⚠️ **`docker compose up -d` 로 되돌리려 하지 말 것.** 운영 스택은 k3s 에 있고, compose 로 띄우면
  게이트웨이가 이중화되거나 빈 도커 볼륨을 물고 올라온다(791 헤더 주석 참조).

### 2-3. 재발 방지 — develop revert MR (정석, 이것까지 해야 끝)

**2-2는 임시 지혈이다.** develop HEAD에는 여전히 문제 커밋이 있으므로, 누군가 develop에 푸시하는 순간 파이프라인이 문제 코드(+새 커밋)를 다시 빌드·배포한다. 반드시 이어서:

```bash
# 문제 머지커밋을 revert하는 브랜치 생성(-m 1: 머지의 첫 부모=develop 쪽을 기준으로 되돌림)
git fetch origin develop
git switch -c hotfix/revert-<이슈번호> origin/develop
git revert -m 1 <문제 머지커밋SHA>
git push -u origin hotfix/revert-<이슈번호>
# → GitLab에서 develop 대상 MR 생성 → 머지되면 파이프라인이 "문제 코드가 빠진 develop"을 자동 재배포
#   (이 자동 배포가 2-2의 수동 retag 상태를 자연스럽게 덮어써 정상 흐름으로 복귀한다)
```

- 원인 커밋 작성자에게 MM으로 상황 공유(어떤 SHA에서 어떤 증상 → revert MR 링크).
- 2-0에서 "migration 이미 적용됨"이었다면 revert MR에 **스키마 호환 여부 리뷰**가 필수다 — revert된 구 코드도 신 스키마 위에서 돌게 되기 때문. 필요하면 revert 대신 fix-forward(수정 MR)를 택한다.

|---|---|---|---|
| MM ❌ + `💥 Build & Test — backend` / `💥 Docker Build` / `💥 Test — ai (import smoke)` | **직전 정상 버전이 그대로 운영 중** (develop이어도 배포 스테이지 도달 전 중단) | 서버 조치 불요. 코드 수정 → 재푸시 | 파이프라인이 배포 전에 끊는 게 설계 의도(운영 보호 게이트). 라벨은 Jenkinsfile 실제 stage명 그대로 |

## 4. 향후 개선 제안 (Jenkinsfile — 이번 이슈에선 문서화만, 미수정)

이번 190은 문서화 이슈라 Jenkinsfile을 건드리지 않았다. 아래는 다음 인프라 이슈 후보:

1. **롤백 stage 파라미터화** — `ROLLBACK_SHA` 파라미터를 받아 2-2의 retag+`up -d`만 수행하는 별도 잡(또는 스테이지). 새벽에 사람이 SSH로 수동 태깅하는 절차 자체를 없앤다. 수동 절차는 오타 한 번(`dodam-backend`만 retag하고 nginx 누락 등)이 곧 미검증 조합 배포다.
2. **`:SHA` 태그 보존 정책** — 현재 무제한 축적(2026-07-23 시점 이미지 147개·14.4GB, 그중 76%가 미사용). `post { always }`의 `docker image prune -f`는 dangling만 지우고 태그된 SHA 이미지는 못 지운다. "최근 N개(예: 10개) SHA만 유지" 정리 스텝 추가 필요 — 단, MM에서 아직 참조 가능한 최근 배포분은 남길 것.
3. **backend actuator 도입 + healthcheck 승격** — 현재 TCP 8080 체크는 "부팅됨"만 보장(1-4의 사각지대 원인). actuator `/actuator/health`(내부망 전용)로 바꾸면 DB 연결 등까지 검증된다.
4. **Healthcheck 스테이지에 401 프로브 추가** — 1-3 표의 #2·#3을 파이프라인에 넣으면 "게이트웨이 생존 + 인증 필터 + 시크릿 유효"까지 자동 검증된다. (`/ai/health`만으로는 backend 기능을 안 본다.)
5. **자동 롤백 검토(신중)** — Healthcheck 실패 시 직전 성공 SHA로 자동 retag+재기동. 단 2-0(마이그레이션 적용 여부)을 기계적으로 판단하기 어려우므로, "migration 변경이 없는 빌드에 한해 자동"처럼 조건부로 설계할 것.
6. **`infra/.env` ↔ Jenkins `dodam-env` 드리프트 감지** — 배포 시 두 파일의 **키 목록**(값 말고)을 비교해 다르면 경고. 롤백/수동 조작 시의 설정 불일치 사고(2-2 주의)를 예방한다.
