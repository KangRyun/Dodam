## 1. 이 경보는 무엇을 말하는가

**git에 적어둔 매니페스트와 클러스터에서 실제로 돌고 있는 것이 어긋났다**는 뜻이다.

쿠버네티스는 선언형이지만, **선언과 반영은 별개**다. 이 프로젝트에서 Jenkins 배포 단계는
`kubectl set image` 만 한다 — **이미지 태그만** 바꾼다. 환경변수·ConfigMap·리소스 제한 같은
설정 변경은 **사람이 손으로 반영해야** 한다. 배포용 서비스 계정에 생성·수정 권한을 주지 않은
것은 실수가 아니라 권한 최소화 설계다(`infra/k8s/README.md` ④).

그 "사람이 해야 한다"를 알려주는 장치가 이 게이트다. **고쳐주지는 않는다. 잊는 것만 막는다.**

### 발단 — 2026-07-30 배포 실패

365(스트로크 Mongo 저장)를 머지했다. 매니페스트는 옳았다. 그런데 **아무도 apply 하지 않았다.**

```
매니페스트에 MONGO_APP_PASSWORD 주입이 제대로 선언됨
  → 아무도 apply 안 함
  → 새 파드가 비밀번호를 빈 문자열로 읽음
  → char[] 바인딩 NPE → CrashLoopBackOff
  → ★ maxUnavailable: 0 이라 구 파드가 계속 서빙 → 장애가 없었다
  → 그래서 더 늦게 알았다. 배포가 실패하고 나서야 발견
```

**조용히 실패했다**는 것이 핵심이다. 서비스는 멀쩡한데 설계도와 실물이 갈라져 있었고
아무 신호도 없었다. 이 경보는 그 침묵을 깨기 위한 것이다.

### 왜 중요한가

1. **조용한 실패를 깨운다** — 위 사례처럼 다음 재시작 때 터진다. 그 타이밍은 대개 새벽이다.
2. **git이 진실이어야 복구가 된다** — 서버가 날아가면 git으로 재구축한다. git이 실물과 다르면
   복구한 시스템은 원래와 **다른 시스템**이다. 백업이 있어도 복원이 안 되면 백업이 아닌 것과 같다.
3. **아동 민감정보 서비스다** — 보관기간·접근제한·암호화를 git에 선언해도 클러스터에 반영이
   안 됐으면 **선언만 있고 보호는 없는 상태**다. 감사 관점에서 치명적이다.

## 2. 경보 3종 구분

점검은 **매시 20분(KST)** 에 돈다. Mattermost로 알림이 간다.

| 경보 | 뜻 | 첫 대응 |
|---|---|---|
| `ManifestDriftDetected` | 돌기는 하는데 **2시간째 성공하지 못했다** | 3절 절차 |
| `ManifestDriftCheckNotRunning` | **3시간째 아예 돌지 않았다** | 잡 생성 여부부터 (5절) |
| `ManifestDriftCheckSuspended` | **24시간 넘게 꺼져 있다** | 켜는 절차는 `base/manifest-drift.yaml` 주석 |

`ManifestDriftDetected` 는 **두 가지 원인을 한 경보로 묶은 것**이다. 의도된 설계다 —
어느 쪽이든 사람이 봐야 하기 때문. 메트릭에는 종료 코드가 안 나오므로 **로그로만 판별**한다.

| 종료 코드 | 뜻 |
|---|---|
| `0` | 반영 완료 |
| `1` | **미반영 있음** — 진짜 드리프트 |
| `2` | **점검 자체가 실패** — 권한·연결·토큰 문제. 드리프트가 아니다 |

> ⚠️ **`2` 를 `0` 으로 읽지 말 것.** "점검이 통과했다"가 아니라 "점검을 못 했다"이다.

### ⚠️ 종료 코드를 파이프 뒤에서 읽지 말 것

로컬에서 스크립트를 직접 돌릴 때 가장 쉽게 속는 지점이다.

```bash
./infra/scripts/check-manifest-drift.sh | tail -25; echo "종료코드=$?"
#                                       ↑ 이 순간 $? 는 tail 의 것이 된다
# → 드리프트가 있어도(1) 점검이 깨져도(2) 화면에는 종료코드=0 이 찍힌다
```

셸의 `$?` 는 **파이프라인의 마지막 명령** 종료 코드다. `tail`·`head`·`grep` 은 거의 항상
성공하므로 **1도 2도 전부 0으로 보인다.** 2026-07-31 실제로 이렇게 오독했다.
위의 "`2` 를 `0` 으로 읽지 말 것"과 같은 함정인데, 원인이 파이프라 화면만 봐서는 알 수 없다.

**올바른 방법 — 파이프를 붙이지 않는다:**

```bash
./infra/scripts/check-manifest-drift.sh > /tmp/drift.txt 2>&1; echo "종료코드=$?"
cat /tmp/drift.txt        # 내용은 파일로 따로 본다
```

**꼭 파이프를 써야 한다면** 첫 명령의 코드를 배열에서 읽는다. ⚠️ **셸마다 이름과 인덱스가 다르다.**

```zsh
# zsh (이 서버의 기본 셸) — 소문자, 1부터
./infra/scripts/check-manifest-drift.sh | tail -25
echo "종료코드=${pipestatus[1]}"
```

```bash
# bash — 대문자, 0부터
./infra/scripts/check-manifest-drift.sh | tail -25
echo "종료코드=${PIPESTATUS[0]}"
```

> ⚠️ **zsh 에서 대문자 `PIPESTATUS` 를 쓰면 에러 없이 빈 문자열이 나온다.**
> `종료코드=` 만 찍히는데, 이걸 흘려보면 또 오독한다. 실측(2026-07-31):
> ```
> zsh :  PIPESTATUS[1]=        ← 빈 값
>        pipestatus[1]=1       ← 이게 맞다
> bash:  PIPESTATUS[0]=1       ← 이게 맞다
> ```
> **헷갈리면 위의 리다이렉트 방식을 쓴다.** 그게 셸에 무관하게 항상 옳다.

CronJob 안에서는 이 문제가 없다 — 스크립트를 `exec` 로 직접 실행하므로 종료 코드가 그대로
Job 의 성패가 된다.

## 3. `ManifestDriftDetected` 대응 절차

### 0단계 — ⚠️ 반사적으로 apply 하지 않는다

**게이트는 "어느 쪽이 틀렸는지" 모른다.** git과 클러스터가 다르다는 사실만 안다.

2026-07-31 오전이 정확히 그 경우였다. 클러스터의 `suspend: false` 가 **옳았고 git이 틀렸다.**
그때 apply 했다면 감시가 꺼졌을 것이다 — 정반대 방향이다. 실제 해결은 **git을 고치는 것**이었다.

### 1단계 — 로그부터 본다

```bash
kubectl -n dodam get jobs | grep manifest-drift-check      # 실패한 잡 찾기
kubectl -n dodam logs job/<잡 이름> -c check               # 무엇이 어긋났는지
kubectl -n dodam logs job/<잡 이름> -c fetch               # clone 자체가 됐는지
```

- **"점검 실패" 또는 fetch 단계에서 죽음** → 종료 코드 2. 드리프트가 아니다. **5절**로.
- **필드 목록이 나옴** → 종료 코드 1. 진짜 드리프트. 2단계로.

출력 예시:

```
★ 반영되지 않은 매니페스트 변경이 있다

  CronJob/manifest-drift-check (ns=dodam)
      .spec.suspend  라이브=false  매니페스트=true

  합계: 누락 리소스 0개 · 불일치 필드 1개
```

### 2단계 — 어느 쪽이 옳은지 사람이 정한다

| 상황 | 조치 |
|---|---|
| **git이 옳다** — 매니페스트를 고쳤는데 반영을 안 함 | 클러스터에 반영 → **3단계** |
| **클러스터가 옳다** — 운영 판단을 git에 안 적음 | git을 고친다 → **4단계** |

판단 기준: *"이 값을 지금 이렇게 만든 사람이 의도한 것인가?"*
의도했는데 git에 없다면 git이 뒤처진 것이다.

### 3단계 — 클러스터에 반영 (git이 옳을 때)

**❌ 절대 하지 말 것 두 가지**

```bash
kubectl apply -k infra/k8s/overlays/prod      # ❌ 금지
```
이미지 태그가 `:prod` 로 되돌아가 **지금 배포된 빌드가 무엇이었는지 추적성이 사라진다.**

```bash
kubectl apply -f infra/k8s/base/<파일>        # ❌ 금지
```
base 파일에는 kustomize가 주입하는 `commonLabels`(`app.kubernetes.io/part-of: dodam`)가 없다.
그대로 apply 하면 **라벨이 빠진 채 만들어져 그 자체가 새 드리프트가 된다.**
게다가 `configmap-app.yaml` 이면 prod overlay의 `AI_*_MODE=http` 가 base의 `mock` 으로 회귀한다 —
360 컷오버 직후 TTS가 무음이던 원인이 정확히 이것이다.

**✅ 바뀐 것만 골라서**

| 바뀐 것 | 반영 방법 |
|---|---|
| ConfigMap 키 추가·수정 | `kubectl -n dodam patch cm <name> --type merge -p '{"data":{"K":"V"}}'` |
| Deployment의 env | `kubectl -n dodam set env deployment/<name> --from=secret/dodam-secrets --keys=A,B` |
| 그 외 필드 | 그 필드만 `kubectl -n dodam patch` |
| 새로 생긴 리소스 | 아래 렌더-선별 방식 |

새 리소스는 **오버레이를 렌더한 뒤 필요한 것만 골라** 적용한다. 라벨이 온전하고 이미지 태그도
건드리지 않는다. 자세한 스크립트는 `infra/k8s/README.md` §2 참조.

```bash
cd <저장소 루트>      # ⚠️ 하위 디렉터리에서 상대경로를 쓰면 "path does not exist"
kubectl kustomize infra/k8s/overlays/prod | <Kind/name 으로 선별> \
  | kubectl apply --dry-run=server -f -      # 먼저 dry-run, 확인 후 --dry-run 빼고 재실행
```

> ⚠️ zsh은 따옴표 없는 변수를 단어 분리하지 않는다. 리소스 목록을 `$LIST` 로 넘기면
> **인자 하나로 들어가 아무것도 매칭되지 않는다.** 나열하거나 `${=LIST}` 를 쓴다.

**ConfigMap을 바꿨으면 롤아웃을 직접 건다**

`envFrom` 값은 **파드 기동 시점에만** 읽힌다. ConfigMap을 고쳐도 **도는 파드는 모른다.**

```bash
kubectl -n dodam rollout restart deployment/<name>
```

이걸 빼먹으면 "반영했는데 왜 그대로지?"가 된다.

### 4단계 — git을 고친다 (클러스터가 옳을 때)

운영 상태는 **손이 아니라 매니페스트에 적는다.** 대개 `overlays/prod/` 에 선언한다.

컨벤션대로 develop에서 브랜치를 파고 MR로 머지한다. ⚠️ **점검 잡은 `develop` 브랜치를
clone 한다** — 커밋만 하고 머지하지 않으면 경보는 계속 울린다. **커밋은 절반이고 머지가 반영이다.**

### 5단계 — 확인

정기 실행(매시 20분)을 기다리지 말고 즉석으로 확인한다.

```bash
kubectl -n dodam create job --from=cronjob/manifest-drift-check drift-once
kubectl -n dodam logs job/drift-once -c fetch     # "clone OK" 확인
kubectl -n dodam logs job/drift-once -c check
kubectl -n dodam delete job drift-once            # 확인 후 정리
```

> 이 수동 잡도 CronJob이 **소유**한다(ownerReferences). 성공하면 `lastSuccessfulTime` 이
> 갱신되어 **경보가 해제된다.** "지금 드리프트 없음"이 사실이므로 의도된 동작이다.

**경보는 다음 성공과 함께 스스로 꺼진다.** 실패한 Job을 손으로 지울 필요는 없다
(2026-07-31 이전 규칙에서는 필요했다 — 6절 참조).

## 4. 실제로 겪은 실패 유형

### ⓐ 게이트가 자기 자신을 신고했다 (2026-07-31 오전)

CronJob을 켤 때 `kubectl patch ... '{"spec":{"suspend":false}}'` 로 손으로 풀었다.
git은 `true`, 클러스터는 `false` — **그 차이는 사라지지 않으므로 매시간 울렸다.**

**교훈:** 운영 상태는 overlay에 선언한다. 손으로 푼 상태는 영구 드리프트가 된다.
현재는 `overlays/prod/cronjobs-enable.yaml` 에 선언돼 있다.

### ⓑ "점검 실패"는 드리프트가 아니다 (2026-07-31 오후)

토큰 교체 중 clone이 깨졌다. 로그는 `HTTP Basic: Access denied`.
**매니페스트는 아무 문제가 없었다.** 5절로 갔어야 할 건이다.

### ⓒ 빈 값이 조용히 들어갔다 (2026-07-31 오후)

시크릿을 만들 때 `read` 가 비대화형 셸에서 EOF를 받아 **빈 토큰**이 들어갔고,
`kubectl` 은 **군말 없이 저장했다.** 정기 실행 두 번이 죽고 나서야 알았다.

365의 `MONGO_APP_PASSWORD` 빈 값 → CrashLoopBackOff와 **같은 부류**다.
**빈 값은 조용히 들어가 나중에 터진다.** 방어는 `${VAR:?}` 와 사후 검증(길이·지문)이다.
절차는 `base/manifest-drift.yaml` 의 ② 주석 참조.

## 5. "점검 실패"(종료 코드 2) 대응

드리프트가 아니라 **점검 인프라 자체의 문제**다. 매니페스트는 건드리지 않는다.

```bash
kubectl -n dodam logs job/<잡 이름> -c fetch     # clone 단계 로그
```

| 로그 | 원인 | 조치 |
|---|---|---|
| `HTTP Basic: Access denied` | 배포 토큰 문제 | 아래 토큰 점검 |
| `CreateContainerConfigError` | Secret `dodam-drift-git` 부재 | `base/manifest-drift.yaml` ② 절차로 생성 |
| `Forbidden` / RBAC 오류 | `drift-reader` 권한 | ClusterRole 확인. **`kubectl diff` 를 쓰지 않는 이유가 여기 있다** (아래) |
| 이미지 pull 실패 · 노드 압박 | 클러스터 자원 | `kubectl -n dodam get pod` 로 상태 확인 |

**토큰 점검 — 값을 노출하지 않고**

```bash
kubectl -n dodam get secret dodam-drift-git -o jsonpath='{.data.GIT_TOKEN}' \
  | base64 -d | wc -c                                   # 25 여야 한다(gldt- + 20자)
```

`0` 이면 빈 값 주입(ⓒ). 배포 토큰은 **프로젝트마다 따로**이고 scope는 `read_repository` 여야
한다 — 바로 아래 `read_registry` 만 켜면 토큰은 멀쩡히 발급되는데 clone만 거부된다.
⚠️ `od`/`xxd` 로 꼬리 공백을 보지 말 것 — 토큰 일부가 화면에 찍힌다. 길이 비교로 갈음한다.

**왜 `kubectl diff -k` 를 쓰지 않나**

`kubectl diff` 는 내부적으로 `PATCH ...?dryRun=All` 을 보내는데, 쿠버네티스는 **dry-run도 실제
쓰기와 동일하게 인가**한다. 즉 읽기 권한만으로는 돌지 않고, 돌리려면 ClusterRole에 `patch`
권한이 필요해진다 — **감시 잡이 스스로 클러스터를 바꿀 수 있게 된다.**
점검 스크립트는 `kubectl get` 만 쓰고 **포함(부분집합) 비교**를 한다. 덤으로 서버가 채우는
기본값이 오탐으로 잡히는 문제도 사라진다.

## 6. 경보 설계 메모 (2026-07-31 재작성)

원래 `ManifestDriftDetected` 는 **실패한 Job 오브젝트**를 셌다.
그날 알림이 **11건** 나갔는데 **진짜 매니페스트 미반영은 0건**이었다. 두 군데서 무너졌다.

| 문제 | 증상 |
|---|---|
| 알림이 **잡마다 1건** | 원인 하나에 4건이 나감 |
| **스스로 안 꺼짐** | 실패 Job이 TTL 3일간 남아, 고쳐도 계속 울림. 사람이 `delete job` 해야 조용해짐 |

그래서 `BackupMissing` 과 같은 관례로 바꿨다 — **CronJob의 마지막 성공 시각**을 본다.

```
활성(suspend=0)이고 최근 3시간 안에 스케줄은 됐는데, 2시간 안에 성공한 적이 없는 것
```

- 알림은 **CronJob당 1건**
- 다음 실행이 성공하면 **스스로 해제**
- 성공 임계 2시간 = 매시 실행이므로 **연속 2회 실패**를 뜻한다. 1회로 잡으면 일시적 clone
  실패(종료 코드 2)에도 운다. **대가: 진짜 드리프트를 알아채는 데 최대 1시간이 걸린다.**
  미반영은 장애가 아니므로 그 지연을 감수할 값이 있다고 판단했다.
- 스케줄 절(3시간)은 `ManifestDriftCheckNotRunning` 의 임계와 **일부러 같은 값**이다.
  어긋나면 그 사이 구간을 두 룰 다 놓치는 사각이 생긴다.

> **시끄러운 경보는 무시되고, 무시되는 게이트는 없느니만 못하다** — "감시하고 있다"는
> 잘못된 안심을 주기 때문이다. 경보를 조용하게 유지하는 것은 편의가 아니라 기능이다.

## 7. 절대 하지 말 것 (요약)

| 금지 | 이유 |
|---|---|
| `kubectl apply -k overlays/prod` | 이미지 태그가 `:prod` 로 회귀 — 배포 추적성 소실 |
| `kubectl apply -f base/<파일>` | `commonLabels` 누락 → 그 자체가 드리프트. `AI_*_MODE` 회귀 |
| `kubectl patch cronjob ... suspend` | 영구 드리프트. 운영 상태는 overlay에 선언 |
| 종료 코드 `2` 를 통과로 읽기 | 점검을 **못 한 것**이지 통과한 게 아니다 |
| `스크립트 \| tail` 뒤에서 `$?` 읽기 | `tail` 의 코드다. **1도 2도 0으로 보인다** (2절) |
| zsh 에서 대문자 `PIPESTATUS` | 에러 없이 **빈 값**. zsh 는 소문자 `pipestatus`, 1부터 |
| 로그 안 보고 apply | 클러스터가 옳은 경우가 있다 (4절 ⓐ) |
| `kubectl diff -k` | dry-run도 쓰기 권한이 필요 — 감시 잡에 patch 권한을 주게 된다 |
| ConfigMap 반영 후 롤아웃 생략 | `envFrom` 은 기동 시점에만 읽힌다 |
