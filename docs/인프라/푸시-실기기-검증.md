# 푸시 실기기 검증 (Android)

> Jira: `S15P11B209-617`(앱 FCM 설정·수신 검증) · 선행 `616`·`619` 완료
> 계약: `docs/api/push-notification-delivery-contract.md`
> 최종 수정: 2026-07-28

앱이 FCM Token을 등록하고 계약 형식(data-only) 메시지를 받아 표시·이동하는지 실기기로 확인한다.

**단계 A**(이 문서)는 BE 발송 코드(`556`) 없이도 가능하다. 발송을 사람이 대신하기 때문이다.
**단계 B**(분석 완료 → 자동 발송 E2E)는 556 머지 후에 한다.

## 0. 준비물

| 항목 | 확인 |
| --- | --- |
| Android 실기기 (에뮬레이터는 Google Play 이미지여야 FCM 동작) | |
| Firebase Service Account JSON | Firebase 콘솔 ▸ 프로젝트 설정 ▸ 서비스 계정 ▸ **새 비공개 키 생성** |
| 백엔드 접속 가능한 앱 빌드 | |

⚠️ **Service Account JSON은 개인키다.** 저장소에 커밋하지 않는다(`infra/secrets/`는 `.gitignore` 대상).
배포 서버 원본은 `/etc/dodam/secrets/fcm-service-account.json` 권한 `600`.
운영(k3s)에서 backend 가 실제로 읽는 것은 그 경로가 아니라 **Secret `dodam-fcm` 이 마운트한
`/run/secrets/fcm-service-account.json`** 이다 — 원본을 두는 것만으로는 발송이 켜지지 않는다.
**서버 설정 절차는 7절.**

## 1. 앱 실행과 Token 등록

```bash
cd frontend/mobile
flutter run --dart-define=API_BASE_URL=<백엔드 주소> --dart-define=PUSH_LOG_TOKEN=true
```

`PUSH_LOG_TOKEN=true`는 **발송 대상 Token을 로그에 노출**한다. 평소에는 길이만 남기므로
(계약 §5.4) 검증할 때만 켠다.

1. 로그인 → **알림 권한 팝업이 뜨는지 확인하고 허용**
   - Android 13+ 런타임 권한이다. 거부해도 앱과 알림함은 정상 동작해야 한다(계약 §4.2).
   - Android 12 이하는 팝업 없이 `granted`가 바로 찍히는 것이 정상이다.
2. 진단 로그 확인 — DevTools **Logging** 탭에서 `push`로 필터하거나
   `flutter logs`/`adb logcat -s flutter`에서 검색한다.

   | 로그 | 의미 |
   | --- | --- |
   | `Firebase 초기화 완료` | 푸시 사용 가능 |
   | `보호자 세션 아님` | 로그인·역할 문제로 시작 안 함 |
   | `pushSetup 미주입` | Firebase 초기화 실패 |
   | `알림 권한 = granted` | 권한 통과 |
   | `⚠️ 검증용 FCM Token 노출: …` | **이 값을 발송에 쓴다** |
   | `푸시 작업 실패(무시)` | 등록 실패 — 없으면 등록 성공 |

3. 서버 로그에서 `POST /api/v1/notifications/device-tokens` **200**과 응답 `registered`를
   교차 확인한다(신규·갱신 구분).

> 에뮬레이터는 **Google Play/Google APIs 이미지**여야 FCM Token이 발급된다. 순수 AOSP
> 이미지면 `FCM Token 발급 실패` 로그가 찍힌다.

> Token 등록은 **보호자 세션이 확정된 뒤**에만 일어난다. 로그인 전에는 등록되지 않는 것이 정상이다.

## 2. 테스트 발송

Firebase 콘솔의 '테스트 메시지'는 `notification` 페이로드를 실어 보내 **우리 계약(data-only)과
맞지 않는다.** 아래 스크립트를 쓴다.

```bash
pip install google-auth requests

python3 infra/scripts/send-test-push.py \
  --credentials /path/to/fcm-service-account.json \
  --token <기기 FCM Token>
```

발송 전에 페이로드만 보려면 `--dry-run`을 붙인다.

| 옵션 | 용도 |
| --- | --- |
| `--type` | 알림 유형 9종 중 선택 |
| `--resource-type` / `--resource-id` | 이동 대상 지정(쌍으로만 유효) |
| `--notification-id` | 중복 표시 방지 확인용 |

## 3. 확인 항목

### 3.1 포그라운드 표시
앱을 열어 둔 채 발송 → 알림이 뜬다.
- data-only라 OS가 자동 표시하지 않고 **앱이 직접 띄운다**. 안 뜨면 파싱 실패를 의심한다.

### 3.2 백그라운드·종료 표시
앱을 홈으로 내리거나 종료한 뒤 발송 → 알림이 뜬다.
- 종료 상태 표시는 백그라운드 격리(isolate)가 담당한다.

### 3.3 탭 라우팅
```bash
python3 infra/scripts/send-test-push.py --credentials <키> --token <토큰> \
  --resource-type REPORT --resource-id <실제 리포트 ID>
```
알림 탭 → **리포트 상세**로 이동한다. `DRAWING_SESSION`이면 활동 상세로 간다.

자원 없이 보내면(기본값) **아무 화면도 강제로 열지 않는다.** 서버가 준 자원과 무관한 화면을
여는 것보다 앱만 열린 채 두는 편이 낫다는 계약 결정이다(§4.3). 알림함 화면(`499`)이 붙으면
그쪽으로 보낸다.

### 3.4 중복 방지
같은 `--notification-id`로 두 번 발송 → **한 번만 표시된다**.

### 3.5 아동 모드 차단 ★가드레일
아동 모드 화면(`/child/...`, 그리기·대화 등)에 들어간 상태로 발송한다.

- **알림이 표시되지 않아야 한다.** 활동 중 알림이 아이 화면을 덮거나, 위험 관련 문구가
  아이에게 노출되면 안 된다(CLAUDE.md 9절·4절).
- 보호자 모드로 돌아온 뒤 알림함에 해당 알림이 남아 있으면 정상이다 — 푸시는 사본이고
  원본은 알림함에 있다.

### 3.6 권한 거부 경로
앱 데이터 삭제 후 재실행 → 권한 **거부** → 앱이 정상 동작하고 알림함을 쓸 수 있는지 확인한다.
Token 등록을 강행하지 않는다.

### 3.7 계약 위반 메시지 폐기
`--dry-run`으로 페이로드를 뽑아 `type`을 `UNKNOWN`으로 바꿔 직접 발송하면
**아무것도 표시되지 않아야 한다**(fail-closed).

## 4. 죽은 Token 정리 확인

앱을 삭제한 뒤 같은 Token으로 발송하면 FCM이 `UNREGISTERED`를 돌려준다.
스크립트가 HTTP 200이 아닌 응답과 함께 종료한다.

서버 측 자동 비활성화는 **556 또는 631 범위**다(계약 §5.3). 이 단계에서는 FCM 응답 확인까지만 한다.

## 5. 단계 B — E2E (556 머지 후)

1. **서버 발송 설정**이 켜져 있어야 한다 — 절차는 아래 **7절**. compose 시절의 `.env` 두 줄이
   아니라 **k8s Secret 2개**다.
2. 분석 완료를 유발 → 자동 푸시 수신 → 탭 → 리포트 이동
3. 알림함에 같은 `notificationId`가 있는지 대조. `deliveryStatus`가 `PENDING`에 머물면
   **발송 경로에 아예 못 들어간 것**이다(7-3 판정표).

> ⚠️ `PUSH_DEVICE_TOKEN_ENCRYPTION_KEY`를 나중에 교체하면 기존 암호문을 복호화할 수 없어
> (GCM 인증 실패) 모든 기기가 재로그인해야 발송 대상이 된다. **발송을 켜기 전에 확정한다.**

## 7. 서버 발송 설정 — k8s Secret 2개 (S15P11B209-774)

> ⚠️ **이 절이 있는 이유.** 619(compose 기준 시크릿 구성)가 **완료로 닫힌 채** 2026-07-29
> k3s 컷오버 때 넘어오지 않았고, 그 결과 운영에서 푸시가 **몇 주 동안 한 건도 나가지 않았다.**
> 알림함 행은 정상 생성되니 화면상 아무 문제가 없어 보였고, 경보도 없어 아무도 몰랐다.
> **재구축·재설치 때마다 이 절을 다시 밟을 것.**

### 7-1. 왜 매번 사라지는가

`dodam-fcm` 은 **git 에 없는 out-of-band 시크릿**이다. 매니페스트(`infra/k8s/base/backend.yaml:157-162`)는
이름만 참조하고 정의하지 않는다. 게다가 볼륨이 `optional: true` 라 **시크릿이 없어도 파드가
정상 기동하고 마운트만 조용히 생략된다.**

그래서 이 결함은 다음 어느 것에도 걸리지 않는다:

- 파드 헬스체크 — 통과한다
- `manifest-drift-check` — git 에 없는 것은 "빠졌다"고 판정할 수 없다
- 배포 파이프라인 — 이미지 태그만 바꾼다(751 과 같은 구조)

걸리는 것은 **`dodam_push_sending_enabled` 게이지 하나뿐**이고, 그래서 경보 룰
`PushSendingDisabled`(`monitoring-prometheus.yaml` 의 `push.yml`)를 함께 뒀다.

그리고 619 가 "완료"였는데도 시크릿이 없었던 진짜 경로는 아마 이것이다 — 컷오버 후
`sync-secrets.sh` 를 **sudo 없이** 돌렸고, 스크립트가 `SKIP … (정상)` 을 출력하며 넘어갔다.
7-2 의 ★ 를 볼 것. **"정상" 이라고 적힌 출력이 실패를 가리는 것이 이 결함의 본체다.**

### 7-2. 절차 — `sync-secrets.sh` 하나로 끝난다

> 📌 **2026-08-05 정정.** 이 절은 원래 `kubectl create secret` 을 손으로 치라고 안내했다.
> 동작은 하지만 **`infra/.env` 와 클러스터 사이에 드리프트를 만든다** — 그리고 다음에 누가
> `sync-secrets.sh` 를 돌리는 순간 그 손수정이 통째로 되돌아간다(`--from-env-file` + `apply`
> 는 `data` 전체 교체다). 실제로 그 상태가 만들어졌다가 발견돼 정정한다.
> **시크릿의 진실은 언제나 `infra/.env` 다. 클러스터를 직접 고치지 않는다.**

`sync-secrets.sh` 는 `dodam-secrets` 뿐 아니라 **`dodam-fcm` 까지 만든다** — `.env` 의
`FCM_CREDENTIALS_HOST_PATH` 가 가리키는 파일이 있으면 그것으로 시크릿을 생성한다
(`infra/scripts/sync-secrets.sh` 의 "③ FCM 자격증명" 블록). 따로 만들 필요가 없다.

```bash
# ① .env 를 고친다 — 여기가 원본이다
APP_PUSH_FCM_ENABLED=true
FCM_CREDENTIALS_HOST_PATH=/etc/dodam/secrets/fcm-service-account.json

# ② 자격증명이 쓸 만한지 확인 (개인키는 출력하지 않는다)
sudo jq -r '{type, project_id, client_email}' /etc/dodam/secrets/fcm-service-account.json

# ③ 동기화 — sudo -E 다. 이유는 아래 ★
sudo -E infra/scripts/sync-secrets.sh infra/.env --dry-run
sudo -E infra/scripts/sync-secrets.sh infra/.env

# ④ 롤링 재시작 — replicas 2 · maxUnavailable 0 이라 무중단
kubectl -n dodam rollout restart deployment/backend
kubectl -n dodam rollout status  deployment/backend --timeout=300s
```

#### ★ `sudo -E` 가 아니면 조용히 실패한다 — 774 가 몇 주 조용했던 이유

스크립트의 FCM 블록은 `[[ -n "$FCM_PATH" && -s "$FCM_PATH" ]]` 로 파일을 검사한다.
`/etc/dodam/secrets/` 는 **700 root** 라 일반 사용자로 돌리면 `-s` 가 **읽기 실패로 false**
가 되고, 스크립트는 이렇게 출력하고 넘어간다:

```
[sync-secrets] SKIP: FCM 자격증명 없음 — 푸시는 비활성으로 뜹니다(정상).
```

**파일은 멀쩡히 있는데 "없음"으로, 그것도 "(정상)" 이라고 보고한다.** 이 한 줄을 보고
넘어가면 푸시가 꺼진 채로 배포가 끝난다. 반드시 아래를 확인할 것:

| 출력 | 판정 |
| --- | --- |
| `OK: dodam/dodam-fcm 적용 완료` | ✅ 자격증명이 실렸다 |
| `SKIP: FCM 자격증명 없음 … (정상)` | ❌ **실패다.** `sudo -E` 로 다시 돌린다 |

`-E` 를 붙이는 이유는 하나 더 있다 — 스크립트가 `KUBECONFIG` 를 스스로 세팅하지 않아,
그냥 `sudo` 면 root 의 kubeconfig 를 본다.

★ 키 이름 `fcm-service-account.json` 은 `backend.yaml` 의 `items.key` 와 **글자 하나까지
같아야** 마운트된다. 스크립트를 쓰면 이 이름을 스크립트가 고정해 주므로 실수할 여지가 없다 —
손으로 만들지 말아야 할 이유가 하나 더 있는 셈이다.

⚠️ 스위치와 자격증명은 **둘 다** 필요하다. 스위치만 켜고 자격증명이 없으면 기동 로그에 ERROR
를 남긴 채 발송은 여전히 안 된다(`FcmAvailableCondition` 이 `enabled && credentials.usable()`).

### 7-3. 판정

```bash
kubectl -n dodam exec deploy/backend -- \
  curl -s localhost:9404/actuator/prometheus | grep push_sending_enabled
kubectl -n dodam exec deploy/backend -- ls -l /run/secrets/
kubectl -n dodam logs deploy/backend | grep -i FCM
```

| 관측 | 상태 |
| --- | --- |
| `dodam_push_sending_enabled{configured="true"} 1.0` + `/run/secrets/fcm-service-account.json` 존재 | ✅ 발송 가능 |
| `{configured="false"} 0.0` + INFO `FCM 발송이 꺼져 있습니다` | 스위치 off — ③ 누락 |
| `{configured="true"} 0.0` + ERROR `자격증명을 쓸 수 없어…` | 스위치는 켰는데 자격증명 불가 — ② 누락이거나 키 이름 불일치 |

> `dodam_push_send_total` 은 **첫 발송 시도가 있어야 나타난다.** 게이지가 1인데 이 카운터가
> 없다면 아직 아무것도 안 보낸 것이지 고장이 아니다.

### 7-4. 종단 확인

설정만으로는 끝이 아니다. **새 알림 1건**을 만들어 `deliveryStatus` 가 `PENDING` → `SENT`
(또는 `FAILED`)로 바뀌는지 본다.

- 이미 `PENDING` 인 기존 알림은 **소급 발송되지 않는다.** 설정 반영 뒤 새로 만든 것으로 확인한다
- `FAILED` 면 발송 경로에는 들어갔고 FCM 응답이 실패한 것이다 — 토큰 유효성·쿼터를 본다
