## 1. 무엇을 만드는가

**그림일기 = 아이가 오늘 있었던 일을 그림으로 그리고, 그리는 동안 AI가 옆에서 말을 걸어주는 활동.**

기준 데이터는 이미 있다(`V12__seed_drawing_types.sql`).

| 항목 | 값 |
| --- | --- |
| 코드 | `ART_DIARY` |
| 이름 | 그림 일기 |
| 카테고리 | `GENERAL` |
| 선택 주체 | `BOTH` (보호자·아동 모두 시작 가능) |
| 권장 연령 | 4~12세 |
| 안내 문구 | "오늘 있었던 일이나 기억에 남는 순간을 그림으로 표현해 보세요." |

핵심 차별점은 **그리는 도중의 실시간 대화**다. 아이가 그림을 그리다 잠깐 멈추면 AI가 지금까지 그려진 그림을 보고 말을 건다("이 노란 건 뭐야?"). 아이가 음성으로 답하고 계속 그린다. 이 왕복이 그림일기의 본체이며, 아이가 한 말이 곧 일기 본문이 된다.

## 2. HTP와 정반대 정책이다 — 혼동 방지

두 활동이 같은 세션 구조를 쓰지만 대화 정책은 정반대다. 구현 시 이 대비를 놓치면 한쪽 규칙을 다른 쪽에 잘못 적용한다.

| 항목 | HTP 검사 | 그림일기 |
| --- | --- | --- |
| 그리는 중 대화 | **금지** | **핵심 기능** |
| 대화가 그림에 미치는 영향 | 검사 오염 — 제거해야 할 위험 | 의도된 상호작용 — 목적 그 자체 |
| 대화 시점 | 4장 전부 완료 후 | 그리는 도중 + 완료 후 마무리 |
| 그림 개수 | 4장 고정 묶음 | 1장 |
| 주제 | 집·나무·사람 지정 | 자유(오늘 있었던 일) |
| 그리는 순서 | 고정, 강제 | 없음 |
| 도구 | 검정 `PEN`·지우개만(표준화) | 펜 5종 + 12색 팔레트 + 그라데이션 (§5.1) |
| 감정 선택 | 검사 종료 시 1회 | **시작·종료 2회** (§4.5) |
| 자동 저장 | 완료 시 확정 | **획 단위 상시** (§4.6) |
| 중간 분석 | 사용하지 않음 | **매 질문의 근거로 사용** |
| 반복 주기 | 필요할 때 1회 | 일상적·반복(일기) |

**왜 정반대여도 되는가:** HTP는 표준화된 투사 검사라서 4장이 같은 심리 상태의 산물이어야 한다. 그림일기는 검사가 아니라 표현 활동이다. 아이가 AI와 이야기하면서 그림이 바뀌는 것은 결함이 아니라 아이가 자기 이야기를 확장한 결과다.

## 3. 진행 순서

### 3.1 전체 흐름

```
[준비]   활동 선택(그림일기) → 날짜 확인 → 간단 안내 → 감정 선택 ①(지금 기분)
   ↓
[그리기 + 대화]  ← 이 구간이 동시 진행된다. 화면 전환 없음.
   캔버스 열림
     아이가 그림 → 획 단위 자동 저장(상시, 백그라운드)
     손 멈춤(3초) → 미리보기 스냅샷 저장 → 중간 탐지
       → AI가 말 걸기(질문 1개) → 아이가 음성·선택으로 답
     아이가 계속 그림 → 손 멈춤 → … (최대 3회 반복)
     아이가 먼저 말 걸기도 가능([이야기하기] 버튼)
   ↓
[완료]   그림 완료 → 최종 저장·탐지 → 마무리 질문 1~2개
   ↓
[마무리] 감정 선택 ②(다 그린 뒤 기분) + 제목 → 일기 저장 → 보호자 리포트
```

**그리기와 대화가 같은 화면에서 동시에 일어난다.** 질문이 떠도 캔버스는 닫히지 않는다. HTP처럼 "그리기 단계 / 대화 단계"로 나누지 않는다.

### 3.2 준비 단계

| 순서 | 화면 | 내용 |
| --- | --- | --- |
| 1 | 활동 선택 | 활동 목록에서 `그림 일기` 선택. 아동도 직접 선택 가능(`selectableBy=BOTH`) |
| 2 | 날짜 확인 | 기본값 오늘. 어제 일기를 채우는 경우를 위해 과거 날짜 선택 허용 |
| 3 | 간단 안내 | "오늘 있었던 일을 그려볼까?" / "그리는 동안 내가 궁금한 걸 물어볼 거야" / 음성으로 답할 수 있다는 안내 |
| 4 | **감정 선택 ①** | "지금 기분이 어때?" — `EmotionType` 6종(`HAPPY`·`SAD`·`ANGRY`·`SCARED`·`CALM`·`UNKNOWN`) 복수 선택 + 직접 표현(선택). 건너뛰기 가능. **제목은 받지 않는다**(아직 안 그렸다) |

안내는 HTP처럼 무겁게 3화면 쓰지 않는다. 그림일기는 반복 활동이라 매번 긴 안내를 보면 방해가 된다. **2회차 이후에는 안내를 건너뛴다.** 감정 선택 ①은 2회차 이후에도 유지한다 — 안내와 달리 매번 값이 달라지는 데이터다.

### 3.3 그리기 + 대화 구간 (핵심)

| 순서 | 트리거 | 처리 | 재사용 API |
| --- | --- | --- | --- |
| 5 | **획 하나가 끝날 때마다** | 획 이벤트를 소배치로 즉시 전송 (자동 저장의 본체) | `POST /stroke-batches` |
| 6 | 손 멈춤 3초 (FE debounce) | 현재 캔버스 **미리보기 스냅샷**을 DRAFT로 저장 | `PUT /draft` |
| 7 | DRAFT 저장 성공 | 중간 객체 탐지 요청 (`DRAFT` + `OBJECT_DETECTION` → `INTERMEDIATE` 저장) | `POST /analyses` (구현됨, S15P11B209-144) |
| 8 | 탐지 완료 | 그 탐지 결과를 근거로 질문 1개 생성 → TTS 재생 | `POST /conversations`(최초 1회) → `POST /questions` |
| 9 | 질문 재생 종료 | 마이크 자동 활성 → 아이 음성 답변 | `POST /voice-answers` |
| 10 | 답변 접수 | 아이는 계속 그림 → 순서 5로 돌아감 | — |

**중간 탐지가 이미 구현돼 있다.** `S15P11B209-144` 설계로 `DRAFT + OBJECT_DETECTION` 조합이 허용되고 `INTERMEDIATE` 범위로 저장된다. 3초 debounce는 FE 책임으로 이미 규정돼 있다. 그림일기가 필요로 하는 "지금까지 그린 것을 보고 질문한다"의 재료가 갖춰져 있다는 뜻이다.

#### 자동 저장은 획 단위, 질문은 여전히 멈춤 단위 — 섞지 않는다

순서 5(획 단위 저장)와 순서 6~8(멈춤 → 탐지 → 질문)은 **주기가 다른 별개 경로**다. 획마다 저장한다고 해서 획마다 질문하지 않는다. `AnalysisTriggerReason.STROKE_COUNT`는 §3.4에서 명시적으로 배제했고, 그 판단은 이 변경 뒤에도 그대로다 — 저장은 유실 방지, 질문은 아이 몰입 보호로 목적이 다르다.

### 3.4 질문 타이밍 정책 — 언제 말을 거는가

**아이가 손을 멈췄을 때만 말을 건다. 획을 그리는 중에는 절대 개입하지 않는다.**

그리기에 몰입한 아이를 중간에 끊으면 집중이 깨지고, 그림일기의 목적(아이가 자기 이야기를 그림으로 펼치는 것)을 방해한다. `AnalysisTriggerReason` Enum에 이미 `PAUSE`, `INTERVAL`, `STROKE_COUNT`, `CHANGE_RATIO`, `USER_REQUEST`가 정의돼 있는데, 그림일기는 이 중 **`PAUSE`와 `USER_REQUEST`만 사용한다.**

| 트리거 | 사용 | 이유 |
| --- | --- | --- |
| `PAUSE` | **사용** | 아이가 스스로 멈춘 순간 = 개입해도 안전한 유일한 시점 |
| `USER_REQUEST` | **사용** | 아이가 [이야기하기] 버튼으로 먼저 말을 걸 때. 아동 주도를 막지 않는다 |
| `INTERVAL` | 사용 안 함 | 시간이 됐다고 끼어들면 몰입 중에 말을 걸게 된다 |
| `STROKE_COUNT` | 사용 안 함 | 획 수는 몰입 여부와 무관 |
| `CHANGE_RATIO` | 사용 안 함 | 많이 그렸다는 건 오히려 몰입 신호 |

#### 질문 횟수 제한

| 구간 | 최대 질문 수 | 근거 |
| --- | --- | --- |
| 그리는 중 | **3개** | 말 걸기가 잦으면 그리기가 아니라 문답이 된다 |
| 완료 후 마무리 | **2개** | 그림 전체를 보고 묻는 질문(예: "제목을 붙이면 뭐라고 할까?") |
| 합계 | **5개** | `maxQuestionCount=5`로 설정. 서버 상한 10 이내 |

아이가 [이야기하기]로 먼저 말을 건 것은 이 한도에 넣지 않는다. 아이 주도 발화를 한도로 막으면 안 된다.

#### 멈춤이 없으면 질문도 없다

아이가 한 번도 멈추지 않고 다 그리면 그리는 중 질문은 0개다. 이건 정상이다. 억지로 끼어들지 않고 완료 후 마무리 질문만 한다.

### 3.5 완료·마무리

| 순서 | 단계 | 처리 | API |
| --- | --- | --- | --- |
| 11 | 그림 완료 | 최종 이미지 저장 + 최종 객체 탐지 | `POST /drawing-complete` |
| 12 | 마무리 질문 1~2개 | 그림 전체를 근거로 질문 | 기존 대화 계속 사용 |
| 13 | **감정 선택 ②** + 제목 | "다 그리고 나니 기분이 어때?" 감정 복수 선택 + 제목 입력(또는 음성으로 말한 것을 제목 후보로 제시) | `PUT /reflection` (기존 §10.9) |
| 14 | 일기 저장 | 활동 완료 처리 + 보호자 리포트 생성 | `POST /complete` |

**제목은 그림일기에서 받는다.** HTP는 주제가 지정돼 있어 제목이 무의미하지만, 그림일기는 아이가 붙인 제목이 일기의 일부다.

#### 감정을 두 번 받는 이유

종이 그림일기가 원래 그런 형식이다 — 날짜와 오늘 기분을 먼저 적고, 그리고 나서 마무리를 적는다. 기능적으로도 두 값이 다른 것을 담는다.

| | 감정 ① (시작) | 감정 ② (종료) |
| --- | --- | --- |
| 담는 것 | 활동에 들어올 때의 상태 | 그리기·대화를 마친 뒤의 상태 |
| 제목 | 받지 않음 | 받음 |
| 건너뛰기 | 가능 | 가능 (기존 `skipped=true`) |

**두 값의 차이를 AI가 해석하지 않는다.** "슬픔 → 행복이므로 활동이 도움이 됐다" 같은 인과 추정은 §13.4가 금지하는 진단형 산출물이다. 리포트에는 **두 시점을 나란히 사실로만** 보여주고, 의미 부여는 보호자·전문가 몫으로 남긴다. 감정 ①이 없으면(건너뜀) 비교 표시 자체를 하지 않는다.

### 3.6 일기 본문은 아이가 한 말로 만든다

그림일기의 결과물은 `그림 + 아이가 한 말`이다.

- 대화에서 아이가 실제로 말한 문장을 그대로 일기 본문 재료로 쓴다.
- **AI가 아이 말을 요약하거나 매끄럽게 고쳐 쓰지 않는다.** 실제 발화와 AI 생성물을 섞지 않는 원칙(§11.3 "실제 발화와 AI 요약을 구분")을 그림일기에서도 지킨다. 아이가 "공원에서 강아지 봤어"라고 했으면 그 문장이 그대로 남는다.
- STT가 확정하지 못한 발화는 추정해서 채우지 않고 그 사실을 남긴다(기존 `sttNeedsConfirmation` 재사용).

## 4. 상태 모델과 구조적 충돌

### 4.1 발견한 충돌 — 현재 코드로는 이 흐름이 한 바퀴도 돌지 않는다

`ConversationStartDrawingSession`(백엔드)이 다음 두 가지를 강제한다.

```java
// canStartConversation(): 대화 시작 가능 조건
currentStage == DrawingStage.ANALYZING || currentStage == DrawingStage.CONVERSING

// 대화를 시작하면
currentStage = DrawingStage.CONVERSING;
```

한편 그리기 관련 API 세 개가 **모두 같은 판정 하나를 공유**한다. 코드로 확인한 결과 차단 범위가 중간 탐지 하나가 아니었다.

```java
// DrawingSession.java:138-142
public boolean isSnapshotUploadable() {
  return deletedAt == null
      && sessionStatus == DrawingSessionStatus.IN_PROGRESS
      && currentStage == DrawingStage.DRAWING;
}
// :150-152  획 배치
public boolean canAcceptStrokeBatch() { return inputMethod == CANVAS && isSnapshotUploadable(); }
// :160-162  분석 요청
public boolean isAnalysisRequestable() { return isSnapshotUploadable(); }
```

| API | 판정 | 대화 시작 후 |
| --- | --- | --- |
| `POST /stroke-batches` (DRAWING-04) | `canAcceptStrokeBatch()` | **차단** |
| `PUT /draft` (DRAWING-05) | `isSnapshotUploadable()` | **차단** |
| `POST /analyses` (중간 탐지) | `isAnalysisRequestable()` | **차단** |

두 조건을 합치면 이렇게 된다.

1. 아이가 그림 → 세션 `DRAWING` → 획 저장·중간 탐지 성공
2. 그 탐지로 대화 시작 → **세션이 `CONVERSING`으로 바뀐다**
3. 아이가 계속 그림 → **획 저장부터 거부된다**(세션이 `DRAWING`이 아니다)

즉 질문 1개가 나가는 순간부터 **아이가 계속 그려도 획이 서버에 저장되지 않는다.** 두 번째 질문의 근거가 없는 정도가 아니라 그림 자체가 유실된다. 획 단위 자동 저장(§4.6) 요구와도 정면으로 부딪힌다.

명세 §12.2도 같은 제약을 규정한다("현재 단계가 `ANALYZING` 또는 `CONVERSING`일 때만 가능하다"). 이 제약은 HTP형 흐름(다 그린 뒤 대화)을 전제로 만들어졌고, 그리면서 대화하는 활동은 고려되지 않았다.

#### 탈출구가 하나 있지만 써서는 안 된다

정본에 `CONVERSING → DRAWING` 전이가 이미 있다(§10.1 말미). 진입점은 **CONV-08 건너뛰기 하나뿐**이다.

```json
{ "questionMessageId": 803, "reason": "CHILD_REQUEST", "returnToDrawing": true }
```

기술적으로는 이걸로 왕복이 돈다. 그러나 이 API의 의미는 "질문을 건너뛰고 다시 그리러 간다"이고 `reason`이 필수다. 아이가 **답을 한 뒤** 계속 그리는 정상 흐름에 쓰면 답변한 질문이 건너뛴 것으로 기록되고(`isSkipped`, §12.9) 대화 요약 `skippedQuestionCount`가 실제와 어긋난다. 리포트에 들어가는 값이라 데이터 오염이다. **무손실 복귀 경로가 따로 필요하다.**

### 4.2 해결안 — 그리는 동안 `DRAWING`을 유지한다

**동시 대화형 활동에서는 대화가 시작돼도 `currentStage`를 `DRAWING`으로 유지한다.**

| 변경 대상 | 내용 |
| --- | --- |
| 대화 시작 조건 | `DRAWING` 단계에서도 대화 시작을 허용 |
| 대화 시작 시 단계 전환 | 동시 대화형 활동은 `CONVERSING`으로 바꾸지 않는다 |
| 중간 탐지 조건 | **변경 불필요** — `DRAWING`을 유지하므로 기존 검증을 그대로 통과한다 |

이 방식을 택한 이유: 중간 탐지 쪽 검증을 건드리지 않고 한쪽만 고치면 된다. 반대로 "중간 탐지를 `CONVERSING`에서도 허용"하는 방향은 HTP를 포함한 모든 활동에서 대화 중 그림 변경을 허용하게 되어 검사 오염 방지 설계와 충돌한다.

`currentStage`의 의미도 이 편이 정확하다. 그림일기에서 아이는 실제로 **그리는 중**이고, 대화는 그리기를 멈추게 하는 별개 단계가 아니라 그리기와 병행하는 활동이다.

### 4.3 상태 흐름

```
IN_PROGRESS/DRAWING   ← 그리기 + 대화가 이 단계에서 동시 진행
    (DRAFT 저장 → 중간 탐지 → 질문 → 답변)  ×N
       ↓ 그림 완료 (POST /drawing-complete)
IN_PROGRESS/ANALYZING   최종 탐지
       ↓
IN_PROGRESS/CONVERSING  마무리 질문 1~2개
       ↓
IN_PROGRESS/REFLECTION  감정 선택 + 제목
       ↓
IN_PROGRESS/REPORTING   리포트 생성
       ↓
COMPLETED/COMPLETED
```

대화 세션은 세션당 1개(`uk_conversation_sessions_drawing_session_id`)로 유지된다. 그리는 중 대화와 마무리 대화가 **같은 대화 세션에 이어서** 쌓이므로 이 제약을 바꿀 필요가 없고, `maxQuestionCount=5`가 전체 질문 수를 관리한다.

### 4.4 요청 빈도 제어

세 가지 제약이 겹친다.

| 제약 | 값 | 출처 |
| --- | --- | --- |
| FE debounce | 마지막 저장 후 3초 무변경 | S15P11B209-144 설계 |
| 중간 분석 throttle | 최근 성공 분석 후 5초 이내 재요청 제한 | 명세 §11.2 |
| 같은 asset 중복 분석 | `PROCESSING`/`SUCCESS` 있으면 409 | S15P11B209-144 |

따라서 **FE는 중간 탐지 요청 간격을 최소 5초 이상으로 유지해야 한다.** 3초 debounce만 지키면 throttle에 걸려 429가 난다. 이 정책은 FE 담당자에게 명시적으로 전달할 항목이다.

429는 오류로 표시하지 않는다. 아직 물어볼 때가 아니라는 뜻이므로 조용히 다음 멈춤을 기다린다.

### 4.5 두 번째 충돌 — 감정은 지금 세션당 1회만, 그것도 REFLECTION에서만

감정 2회는 현재 계약과 정면으로 부딪힌다. 명세 §10.9(감정·제목 저장)는 이렇게 돼 있다.

- 요청 Body가 `title` + `selectedEmotions` + `expressedEmotionText` + `skipped` **한 벌**이다. 시점을 구분할 필드가 없다.
- "성공 시 `currentStage=REPORTING` 직전 준비 상태인 `REFLECTION`을 반환한다" — **호출하면 세션이 REFLECTION으로 전환된다.**
- 세션 조회·리포트 응답의 `selectedEmotions`가 단수 필드다(§10.4 응답 필드 목록, §13 리포트 목록·상세).

그대로 두고 시작 시점에 이 API를 부르면 **아직 한 획도 안 그렸는데 세션이 마무리 단계로 넘어간다.** §4.1과 성격이 같은 충돌이다 — 계약이 "그리기가 끝난 뒤 감정"이라는 단일 흐름만 가정하고 만들어졌다.

**해결안: 감정 기록에 시점 구분을 넣고, 시작 시점은 단계를 전환하지 않는다.**

| 변경 대상 | 내용 |
| --- | --- |
| 요청 | `checkpoint: PRE \| POST` 추가. `PRE`는 `title`을 받지 않는다 |
| 단계 전환 | `POST`만 `REFLECTION`으로 전환. `PRE`는 **현재 단계를 유지**한다 |
| 호출 가능 단계 | `PRE`는 `DRAWING`에서, `POST`는 기존과 동일 |
| 중복 | 같은 `checkpoint`로 재호출하면 마지막 값으로 덮어쓴다(시점당 1건) |
| 조회 응답 | `selectedEmotions` 단수 필드는 **`POST` 값을 유지**하고, 시점별 전체는 별도 필드로 추가 |

마지막 행이 핵심이다. `selectedEmotions`를 배열의 배열로 바꾸거나 의미를 바꾸면 **기존 화면·리포트·FE 코드가 전부 깨진다**(세션 상세·활동 기록 목록·리포트 목록·리포트 상세 4곳에서 쓰인다). 기존 필드는 종료 시점 값으로 두고 시점별 데이터를 덧붙이는 쪽이 additive라서 안전하다.

별도 신규 엔드포인트를 파는 방향도 가능하지만 권하지 않는다. 저장 대상·검증 규칙·금지 정책(`UNKNOWN` 배타, 보호자 대리 입력 금지)이 완전히 같아서 두 곳에 같은 규칙을 중복 구현하게 된다.

### 4.6 획 단위 자동 저장 — 무엇을 획마다 저장하는가

"획마다 저장"을 문자 그대로 **캔버스 이미지를 획마다 업로드**하는 것으로 구현하면 안 된다. `PUT /draft`는 `multipart/form-data`로 미리보기 이미지 전체를 올려 마지막 저장본을 통째로 교체한다(§10.6). 획 하나에 이미지 한 장이면 아이가 100획 그릴 때 이미지 100장을 올리게 된다.

**획 단위 지속성은 `POST /stroke-batches`가 이미 담당한다.** 이 API는 좌표·도구·색상·굵기·필압까지 이벤트 단위로 저장하므로, 여기에 실려 서버에 도달한 획은 그 시점에 이미 영구 저장된 것이다. 즉 획 단위 자동 저장은 **전송 주기를 조이는 문제**이지 새 저장 수단이 필요한 문제가 아니다.

| 대상 | 주기 | 목적 |
| --- | --- | --- |
| 획 이벤트 (`POST /stroke-batches`) | **획 5개 또는 2초 중 먼저 도달하는 쪽** | 유실 방지. 앱 백그라운드 진입·강제 종료 직전·완료 시 즉시 flush |
| 미리보기 스냅샷 (`PUT /draft`) | 손 멈춤 3초 | 복구 화면 표시 + 중간 탐지 입력 |

획 1개마다 HTTP 요청을 보내지 않는 이유는 네트워크 왕복 비용이다. 5획/2초면 최악의 경우 유실이 획 4개 또는 2초 분량이고, 아이가 손을 멈추는 순간(=대부분의 이탈 시점) flush가 걸리므로 실질 유실은 그보다 작다.

**기존 계약으로 충분하다.** 이벤트 최대 500개·1 MiB 상한(§10.5)은 5획 배치에 걸릴 일이 없고, `batchSequence` + checksum 멱등 규칙이 재전송 중복을 막아준다. 계약 변경 없음.

## 5. 화면·상호작용 설계

### 5.1 캔버스 도구 사양

**먼저 확인한 것: 이 사양 전체가 계약 변경 없이 들어간다.** 획 이벤트의 `tool`·`eventType`은 Enum이 아니라 **패턴 제약이 붙은 문자열**이고, DB도 `VARCHAR(30)`에 CHECK 제약이 없다.

```java
// StrokeEventRequest.java:28-39
@NotBlank @Size(max = 30) @Pattern(regexp = "[A-Z][A-Z0-9_]*") String eventType,
@Size(max = 30)           @Pattern(regexp = "[A-Z][A-Z0-9_]*") String tool,
@Pattern(regexp = "^#[0-9A-Fa-f]{6}([0-9A-Fa-f]{2})?$")        String color,
```
```sql
-- V3__normalize_json_columns.sql:183-184
event_type VARCHAR(30) NOT NULL COMMENT '이벤트 유형',
tool       VARCHAR(30) NULL     COMMENT '그리기 도구',
```

즉 새 도구 코드·새 이벤트 코드·임의 hex 색상은 **지금 서버가 이미 받는다.** 남는 일은 명세 변경이 아니라 **코드 목록을 팀이 합의하고 문서에 고정하는 것**이다. 합의 없이 FE가 임의 문자열을 보내면 행동 분석(`tool_change_count`, 색상 통계)이 집계 불가능한 잡음이 된다.

#### 펜 5종

| 표시 | `tool` 코드 | 특성 | 필압 |
| --- | --- | --- | --- |
| 연필 | `PENCIL` | 얇고 거친 질감, 필압에 따라 농도 변화 | 사용 |
| 볼펜 | `PEN` | 균일한 굵기, 불투명 | 무시 |
| 크레용 | `CRAYON` | 굵고 불투명, 거친 가장자리 | 약하게 사용 |
| 붓 | `BRUSH` | 필압·속도로 굵기 변화, 겹칠수록 진해짐 | 사용 |
| 색연필 | `COLORED_PENCIL` | 반투명, 겹칠수록 진해짐 | 사용 |

**볼펜에 신규 코드를 만들지 않고 기존 `PEN`을 쓴다.** 명세 §10.5 예시가 이미 `"tool": "PEN"`이고, HTP 검사가 쓰는 표준 도구도 `PEN`(검정 고정)이다. 코드를 새로 파면 기존 데이터와 두 갈래가 된다.

필압 미지원 기기는 `pressure: null`로 보낸다(§10.5 기존 규칙). `0`으로 보내지 않는다 — 필압 0은 "누르지 않았다"는 유효한 값이라 미지원과 구분돼야 한다.

**필압은 좌표별로 저장된다.** 정본 §10.5 예시는 이벤트 레벨에만 `pressure`를 두지만 실제 구현은 좌표마다 받는다(`StrokePointRequest.java:30`, `stroke_event_points.pressure`, FE `StrokePointDto.pressure`). 붓처럼 **한 획 안에서 굵기가 변하는 도구를 표현할 재료가 이미 있다** — 별도 계약 없이 구현 가능하다.

#### 지우개 — 영역 지우기

| 항목 | 값 |
| --- | --- |
| `eventType` | `ERASE` |
| `tool` | `ERASER` |
| 크기 전달 | 기존 `width` 필드 |
| 방식 | 지나간 자리를 지우는 **래스터 영역 지우개**. 획 단위 삭제(객체 지우개) 아님 |
| 버튼 프리셋 | 가는 8 / 보통 24 / 굵은 56 (3단) |
| 연속 조절 | 슬라이더 4~80, 프리셋과 같은 값을 공유 |
| 미리보기 | 현재 크기를 원형 커서로 캔버스에 표시 |

프리셋과 슬라이더 둘 다 두는 이유: 어린 아이는 슬라이더 미세 조작이 어렵고, 큰 아이는 3단으로 부족하다. 프리셋 버튼을 누르면 슬라이더 위치도 같이 움직여 **두 컨트롤이 같은 값 하나를 가리킨다**(별도 상태로 두면 어긋난다).

> **확인 완료(2026-07-27): `width`는 Flutter 논리 픽셀이다.** 정본 §10.5에 단위가 적혀 있지 않아 확인했더니, 팀 정책은 이미 정해져 있고 명세에 옮겨지지 않았을 뿐이었다 — `drawing_event_journal.dart:156`에 `// Team policy uses the same Flutter logical pixel value as Paint.strokeWidth.`와 문서화 요청 TODO가 달려 있다. DDL도 뒷받침한다: 좌표는 `DECIMAL(8,6)`(0~1용)인데 `width`는 `DECIMAL(8,3)`으로 정수부가 5자리다(`V3:186`).
>
> 따라서 위 지우개 크기 값(8/24/56, 슬라이더 4~80)을 **논리 픽셀 기준으로 그대로 확정**한다. 논리 픽셀은 기기 물리 해상도와 무관하므로 어느 기기에서든 같은 굵기로 보이고, 소수 3자리까지 저장되므로 슬라이더 연속값도 잘리지 않는다. 명세에는 현행을 그대로 적는 문서 보강만 필요하다(해석 변경이 아니므로 breaking 아님) — `2026-07-27-art-diary-contract-design.md` §4.

#### 색상 — 표준 12색 + 그라데이션

기본 팔레트 12색을 항상 노출하고, `[+]` 버튼을 누르면 그라데이션 피커가 열려 임의 색을 고른다.

| # | 이름 | Hex | | # | 이름 | Hex |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 빨강 | `#E53935` | | 7 | 파랑 | `#1E88E5` |
| 2 | 주황 | `#FB8C00` | | 8 | 남색 | `#3949AB` |
| 3 | 노랑 | `#FDD835` | | 9 | 보라 | `#8E24AA` |
| 4 | 연두 | `#7CB342` | | 10 | 분홍 | `#EC407A` |
| 5 | 초록 | `#43A047` | | 11 | 갈색 | `#6D4C41` |
| 6 | 하늘 | `#29B6F6` | | 12 | 검정 | `#212121` |

- 그라데이션 피커로 고른 색도 `color`에 그대로 hex로 실린다 — 계약이 이미 임의 hex를 허용한다.
- 최근 사용 색 4개를 팔레트 옆에 유지한다. 매번 피커를 다시 여는 부담을 없앤다.
- 팔레트는 **기준 데이터로 서버가 내려주는 것이 아니라 클라이언트 상수로 둔다.** 색 12개를 위해 API를 만들 이유가 없고, 바뀔 일도 드물다.

#### 전체 지우기 · 되돌리기

| 기능 | `eventType` | 처리 |
| --- | --- | --- |
| 전체 지우기 | `CLEAR_ALL` | 캔버스를 비운다. `points`는 빈 배열, `tool`·`color`·`width`는 `null` |
| 되돌리기 | `UNDO` | 직전 이벤트 1개 취소. `metrics.undoCountDelta`에 반영(기존 필드) |

- **`points`를 생략하면 안 된다.** `StrokeEventRequest.points`는 `@NotNull`이라 `CLEAR_ALL`처럼 좌표가 없는 이벤트도 `[]`를 실어야 한다. 누락하면 400이다.
- **전체 지우기도 되돌릴 수 있다.** 실수로 눌러 그림 전체를 잃는 것이 아이에게 가장 큰 사고다. `CLEAR_ALL`을 되돌리기 스택에 넣어 1단계 복구를 보장한다.
- 전체 지우기는 **확인 한 번을 받는다**("다 지울까요?"). 되돌리기가 있어도 확인 없이 사라지면 아이가 놀란다.
- 되돌리기 깊이는 **20단계**. 다시하기(redo)는 제공하지 않는다 — 아이 UI에서 undo/redo 두 버튼은 혼동을 준다. `metrics.redoCountDelta`는 계약에 있으므로 `0`으로 보낸다.
- `eventType`은 세션 전체에서 증가하는 `sequence`를 그대로 쓴다. **되돌리기를 해도 sequence를 되감지 않는다** — 되감으면 `STROKE_SEQUENCE_GAP` 검증과 배치 멱등성이 깨진다. 취소는 "취소했다는 이벤트를 추가"로 기록한다.

### 5.2 캔버스 화면 구성

캔버스가 화면 주인이고, 대화는 그 위에 얹힌다.

- **캔버스**: 화면 대부분. 도구·색상은 §5.1 사양(검사가 아니므로 제한 없음)
- **도구 바**: 펜 5종 / 지우개(+크기) / 색상 팔레트 / 되돌리기 / 전체 지우기. 캔버스를 가리지 않는 가장자리 고정
- **AI 말풍선**: 질문이 오면 캔버스를 가리지 않는 영역에 표시 + TTS 자동 재생
- **답변 입력**: TTS 재생이 끝나면 마이크 자동 활성. 선택형 버튼(이모지·색상)도 함께 제공
- **[이야기하기] 버튼**: 아이가 먼저 말을 걸 수 있는 상시 버튼
- **[다 그렸어요] 버튼**: 완료

### 5.3 손이 캔버스에 있는 상태를 고려한다

아이는 한 손에 펜을 들고 있다. 버튼을 정확히 누르기 어렵다.

- TTS 재생 종료 후 **마이크를 자동으로 켠다**(버튼 누르기 요구 안 함). 기존 §12.4가 "TTS 재생 중 마이크 비활성, 종료 후 활성"을 이미 규정한다.
- 침묵으로 녹음을 자동 종료한다(기존 `stopReason=SILENCE` 재사용).
- 답하지 않고 계속 그려도 된다. 무응답은 실패가 아니다 — 일정 시간 뒤 질문을 닫고 다음 멈춤을 기다린다.

### 5.4 대화가 방해가 되면 끌 수 있다

**아이나 보호자가 대화 기능을 끌 수 있게 한다.** 말 걸기를 싫어하는 아이도 있고, 조용히 그리고 싶은 날도 있다. 끄면 순수한 그리기 활동이 되고, 완료 후 마무리 질문만 남긴다(그것도 건너뛸 수 있다).

## 6. 리포트

기존 `ParentActivityReport`(§13.4)를 그대로 쓴다. 그림일기 전용 리포트 타입을 만들지 않는다.

| 항목 | 내용 |
| --- | --- |
| 그림 | 완성 그림 + 썸네일 |
| 아이가 한 말 | 대화에서 나온 실제 발화(요약 아님) |
| 아이가 고른 감정 | **시작·종료 두 시점을 나란히** + 각 직접 표현. 변화에 대한 해석은 붙이지 않는다(§3.5) |
| 제목 | 아이가 붙인 제목 |
| 활동 기록 | 그린 시간·멈춤 횟수·지우기 횟수·되돌리기 횟수·도구 변경 횟수 |
| 보호자 대화 가이드 | "아이가 말한 강아지에 대해 더 물어보세요" 수준의 후속 대화 제안 |
| 한계 고지 | 진단 자료가 아님 |

**중간 분석 결과는 리포트에 넣지 않는다.** 명세 §11.2가 "중간 분석 결과는 질문 생성에 활용할 수 있으나 보호자 리포트로 직접 노출하지 않는다"고 규정한다. 중간 탐지는 어디까지나 질문 재료다.

**일기는 쌓이는 활동이다.** 월별·주별 모아보기는 기존 활동 기록 API(§14 history)로 커버되며 별도 신설이 필요하지 않다. 다만 목록에서 일기 날짜로 정렬·조회하는 요구가 있으면 `activityDate` 필터를 확인해야 한다.

## 7. 기존 자산 재사용 / 신규 필요

### 7.1 그대로 재사용 (변경 없음)

- 세션 생성·임시 저장·획 데이터 수집: `POST /drawing-sessions`, `PUT /draft`, `POST /stroke-batches`
- **캔버스 도구·색상 전체 사양**(펜 5종·지우개·임의 hex 색상·`CLEAR_ALL`·`UNDO`): `tool`/`eventType`이 문자열, `color`가 임의 hex, DB에 CHECK 제약 없음 — **계약 변경 없이 수용**(§5.1)
- 획 단위 자동 저장: `POST /stroke-batches` 전송 주기 조정만으로 충족(§4.6)
- 행동 지표: `metrics.undoCountDelta`·`redoCountDelta`·`eraseCountDelta`·`pauseDurationMsDelta` (기존 필드)
- **중간 객체 탐지**: `POST /analyses` (`DRAFT` + `OBJECT_DETECTION` → `INTERMEDIATE`). S15P11B209-144로 구현 완료
- 최종 완료·탐지: `POST /drawing-complete`
- 대화: 질문 생성, TTS, 음성 답변(STT), 선택형 답변, 건너뛰기, 종료
- 감정·제목 저장: `PUT /reflection`
- 활동 완료·리포트: `POST /complete`, 리포트 조회·PDF
- 활동 기록 목록: history API
- 기준 데이터: `ART_DIARY` (V12 seed 완료)

### 7.2 신규 필요

| 항목 | 범위 | 비고 |
| --- | --- | --- |
| `DRAWING` 단계에서 대화 시작 허용 | `ConversationStartDrawingSession.canStartConversation()` 조건 완화 | **명세 §12.2 변경** |
| 대화 시작 시 단계 전환 억제 | 동시 대화형 활동은 `CONVERSING`으로 바꾸지 않음 | **명세 §12.2 변경** |
| 활동별 대화 정책 구분 | 활동 유형이 "동시 대화형"인지 판별하는 수단(그림 유형 속성 또는 대화 시작 요청 필드) | **명세 변경** |
| 질문 트리거 제한 | `PAUSE`·`USER_REQUEST`만 허용 | 정책 문서화 + 검증 |
| 아이 주도 발화 진입점 | [이야기하기] 요청 처리 | 기존 질문 API로 커버 가능한지 확인 필요 |
| 대화 기능 on/off | 활동 시작 시 대화 사용 여부 선택 | **명세 변경** |
| **감정 2회 기록** | 감정 저장에 `checkpoint: PRE\|POST` 추가, `PRE`는 단계 전환 없음, 조회 응답에 시점별 필드 추가(`selectedEmotions` 단수 필드는 `POST` 값 유지) | **명세 §10.9 변경** (§4.5) |
| **도구·이벤트 코드 목록 합의** | `PENCIL`·`PEN`·`CRAYON`·`BRUSH`·`COLORED_PENCIL`·`ERASER` / `ERASE`·`CLEAR_ALL`·`UNDO` | **계약 변경 없음** — 문서·팀 합의만(§5.1) |
| `width` 단위 명확화 | 픽셀인지 정규화인지 명세에 정의 없음. 지우개 크기 확정 전 확인 필요 | **명세 §10.5 보강**(해석 변경은 breaking) |
| FE 요청 간격 정책 | 중간 탐지 최소 5초 간격, 429는 조용히 무시 / 획 배치는 5획·2초 flush | FE 담당 전달 항목 |
| 캔버스 + 대화 동시 화면 | 말풍선·자동 마이크·[이야기하기] | FE 담당 |
| 도구 바 UI | 펜 5종·지우개 크기(버튼 3단 + 슬라이더)·12색 팔레트 + 그라데이션 피커·되돌리기·전체 지우기(확인 1회) | FE 담당 |

**"동시 대화형" 판별 수단을 어디에 둘지가 설계 결정이다.** 두 방향이 있다.

- **그림 유형 속성으로 둔다**(`drawing_types`에 컬럼 추가): 활동별 정책이 데이터로 관리돼 새 활동 추가가 쉽다. 대신 migration이 필요하다.
- **대화 시작 요청 필드로 둔다**: migration이 없다. 대신 클라이언트가 정책을 결정하게 되어 서버가 강제할 수 없다.

**그림 유형 속성을 권한다.** HTP에서 그리는 중 대화를 막는 것은 검사 타당성 문제라 클라이언트 판단에 맡길 수 없다. 서버가 활동 유형으로 강제해야 한다.

## 8. 미결정 사항과 제안 기본값

| # | 결정 사항 | 제안 기본값 | 근거 |
| --- | --- | --- | --- |
| 1 | 그리는 중 최대 질문 수 | **3개** | 더 많으면 그리기가 아니라 문답이 된다 |
| 2 | 마무리 질문 수 | **1~2개** | 그림 전체를 보고 묻는 질문. 합계 `maxQuestionCount=5` |
| 3 | 질문 트리거 | **`PAUSE` + `USER_REQUEST`만** | 몰입 중 개입 금지 |
| 4 | 멈춤 판정 시간 | **3초** (FE debounce) | S15P11B209-144 기존 정책 유지 |
| 5 | 중간 탐지 최소 간격 | **5초** | 명세 §11.2 throttle과 충돌하지 않는 최소값 |
| 6 | 무응답 처리 | **실패 아님. 질문 닫고 다음 멈춤 대기** | 아이가 답할 의무는 없다 |
| 7 | 대화 on/off 제공 | **제공** | 조용히 그리고 싶은 경우를 막지 않는다 |
| 8 | 일기 본문 AI 요약 | **하지 않음** | 아이 실제 발화를 그대로 남긴다(§11.3 원칙) |
| 9 | 과거 날짜 일기 허용 | **허용** | 어제 일기를 오늘 채우는 것은 일기의 정상 사용 |
| 10 | 동시 대화형 판별 위치 | **`drawing_types` 속성** | 서버가 강제해야 하는 정책이다(§7.2) |
| 11 | 도구·색상 | **펜 5종 + 12색 팔레트 + 그라데이션 피커** (§5.1) | 검사가 아니라 표현 활동. "자유"로만 두면 구현이 확정되지 않아 사양으로 고정 |
| 12 | 2회차 이후 안내 생략 | **생략** | 반복 활동에서 매번 안내는 방해 |
| 13 | 감정 선택 횟수 | **2회(시작·종료)** | 종이 그림일기 형식. 두 값의 차이는 해석하지 않고 병기만(§3.5) |
| 14 | 시작 감정 건너뛰기 | **허용** | 답할 의무를 만들지 않는다. 건너뛰면 리포트에서 비교 표시 자체를 생략 |
| 15 | 획 배치 전송 주기 | **획 5개 또는 2초 중 먼저** | 획 1개마다 HTTP는 과다. 멈춤·백그라운드 진입 시 즉시 flush로 실질 유실 최소화(§4.6) |
| 16 | 지우개 크기 | **버튼 8/24/56 + 슬라이더 4~80 (Flutter 논리 픽셀)** | 프리셋만으론 부족, 슬라이더만으론 어린 아이가 조작 못 함. 두 컨트롤이 같은 값 공유. 단위 확정 근거는 §5.1 |
| 17 | 되돌리기 깊이 | **20단계, redo 없음** | undo/redo 두 버튼은 아동 UI에서 혼동 |
| 18 | 전체 지우기 되돌리기 | **가능(스택에 포함) + 실행 전 확인 1회** | 그림 전체 유실이 가장 큰 사고 |
| 19 | 색상 팔레트 제공 방식 | **클라이언트 상수** | 12색을 위해 기준 데이터 API를 만들 이유가 없다 |
