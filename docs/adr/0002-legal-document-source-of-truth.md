## 컨텍스트

서비스 이용약관 원문이 두 곳에 각각 존재하고, 두 사본을 연결하는 규칙이 어디에도 없었다.

| | 정적 공표본 | DB 약관 레코드 |
|---|---|---|
| 위치 | `infra/nginx/html/legal/terms/index.html` | `consent_terms.content_html` (`term_code='SERVICE_TOS'`, `version='v1'`) — `backend/src/main/resources/db/migration/V29__seed_consent_term_contents.sql` |
| 보는 사람 | 웹 방문자(`frontend/web/src/app/page.tsx`의 `/legal/terms/` 링크), 스토어 심사(`docs/출시/Play-데이터안전-선언-초안.md`) | 앱에서 **실제로 동의하는 사용자**(`consent_terms_screen.dart` → `contentHtml`) |
| 개정 경로 | HTML 편집 → nginx 이미지 재빌드 → gateway rollout | 새 Flyway 마이그레이션 |

783 착수 시점의 실측: **정적 12조 / DB 13조**로 조 번호가 어긋나 있었고, 대응되는 13개 조 중 문장까지 같은 조가 하나도 없었다. 그중 3건은 서로 반대되는 사실을 말하고 있었다(자체 계정 가입 여부 / 전문가 리포트 공유 제공 여부 / 동의 철회 시 즉시 삭제 여부). "제10조에 따라"라는 문장이 어느 사본을 봤느냐에 따라 다른 조항을 가리키는 상태였다.

드리프트를 잡는 장치는 없었다. BE 가드 테스트 2종(`MigrationVersionTest`·`DatabaseMigrationIntegrationTest`)은 DB 쪽 형식만 보고 `infra/nginx/html`을 읽지 않았고, Jenkins 배포 검증은 `/legal/privacy/`가 200을 돌려주는지만 확인한다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| **A. DB(`consent_terms.content_html`)를 정본** (채택) | 동의 증빙이 가리키는 축과 정본이 일치한다. DB본이 이미 실측 기반으로 더 정확하다. 비용은 정적본을 DB에 맞춰 다시 쓰는 1회 작업 |
| **B. 정적 HTML을 정본** | 기각. 정적본이 실제 구현과 3곳 어긋나 있어 정본으로 승격하려면 먼저 고쳐야 하고(= 개정일 변경·재동의 고지 촉발), DB본에만 있는 서술(공동양육 탈퇴 처리, 외부 AI 모델 장애, 탈퇴 후 게시물 익명화, 애플 로그인)을 잃는다. 게다가 동의 증빙 FK가 가리키는 문구는 여전히 DB에 있어 "정본이 아닌 곳에 법적 효력이 붙는" 구조가 남는다 |
| **C. 단일 원문(`docs/legal/*.md`)에서 양쪽을 빌드 타임 생성** | 보류. 드리프트가 구조적으로 불가능해지는 유일한 안이지만 생성기·CI 스텝을 새로 만들어야 하고 팀에 선례가 없다. 문서 수가 2개인 현 규모에서는 비용이 이득을 넘는다 |

## 결정

### 1. 의미의 정본은 DB다

`consent_terms.content_html`이 서비스 이용약관 의미의 정본이다. 근거:

1. **법적 증빙 축이 DB에 있다.** `consent_records.consent_term_id`가 `consent_terms(id)`를 FK로 가리키고(`V1__create_initial_schema.sql`), 사용자가 "무엇에 동의했는가"의 실체는 그 행의 `content_html`이다. 증빙이 가리키는 문구와 정본이 다른 곳에 있으면 소급 정합성이 성립하지 않는다.
2. **DB본이 실측 기반으로 더 정확하다.** 정적본의 사실 오류 3건이 DB본에서는 이미 교정돼 있고, 그 근거가 `V29` 헤더 주석에 코드·스키마 레벨로 명시돼 있다(V6 소셜 전용 인증 / 전문가 공유 경로 부재 / 삭제 워커 미구현).
3. **최신성.** 정적본은 2026-07-28 이후 무수정, DB본은 2026-08-02에 실측을 근거로 재작성됐다.

### 2. "의미"의 정본이지 "형식"의 정본은 아니다

정적 HTML은 `<h2>`·`<ul>`·`<ol>`·`<table>` 마크업을 계속 자유롭게 쓴다. DB 쪽의 `<p>`/`<br>` 제한은 정적본에 전파하지 않는다. 두 사본은 **조 번호·조 제목·각 조가 말하는 내용**이 같으면 되고, 문장 다듬기와 강조 표현은 매체에 맞게 달라도 된다.

DB 쪽 `<p>`/`<br>` 제한은 유지하되 **근거가 바뀌었다.** 원래 이유(앱 평문 변환기가 블록 태그를 줄바꿈으로 처리하지 못함, 447 D7)는 782(`5f9bf3b4941c5398aef96d7ddb29ed687b4f208a`)가 블록 태그 26종을 개행으로 치환하도록 고쳐 해소됐다. 지금 이 제한을 유지하는 것은 **두 사본 대조를 단순하게 유지하기 위한 정책적 선택**이다. 양쪽 마크업이 모두 자유로워지면 대조 비용이 올라간다.

### 3. 개정 절차

약관 문구를 고칠 때는 **항상 두 파일을 같은 커밋에서 고친다.**

1. **DB 쪽 먼저.** `V29`를 수정하지 않고 새 마이그레이션을 추가한다(`V29` 헤더 주석의 규칙). 문구만 다듬으면 같은 `version='v1'`을 UPDATE하고, **동의의 의미나 처리 범위가 바뀌면 새 `version` 행을 INSERT한 뒤 이전 버전을 `is_active=FALSE`로 내린다.** 같은 버전에 의미가 바뀐 문구를 덮어쓰면 이미 기록된 동의 증빙이 실제와 달라진다.
2. **정적본을 맞춘다.** 조 번호·제목을 DB와 동일하게 두고, 문서 머리말의 최종 개정일을 갱신한다.
3. `LegalDocumentConsistencyTest`가 통과하는지 확인한다.

### 4. 드리프트 감지

`backend/src/test/java/com/ssafy/b209/database/LegalDocumentConsistencyTest.java`가 두 파일을 직접 읽어 **조 번호와 조 제목의 목록이 정확히 일치하는지** 단언한다. Docker 없이 도는 순수 파일 테스트다.

**이 테스트가 실제로 돌게 하려면 Gradle 입력 선언이 함께 있어야 한다.** `backend/`는 자체 `settings.gradle`을 가진 독립 Gradle 루트라 `infra/`는 `:test`의 기본 입력에 잡히지 않는다. 선언이 없으면 **정적 약관만 고친 커밋에서 `:test`가 `UP-TO-DATE`로 건너뛰어져 가드가 실행조차 되지 않는다**(783 QA B-1에서 실측으로 확인됐다. 이 이슈의 드리프트를 만든 커밋 `1ef6b586`이 정확히 `infra/`만 건드린 커밋이다). 그래서 `backend/build.gradle`의 `tasks.named('test')`에 `inputs.files(fileTree(project.file('../infra/nginx/html/legal')))`를 선언했다. **이 선언을 지우면 가드는 조용히 무력해진다.**

본문 전문은 비교하지 않는다 — 마크업 문법이 달라 문자열 비교가 불가능하다. 조 번호·제목만 보는 이유는 783에서 실제로 일어난 드리프트가 그 형태였고(조 신설로 번호가 밀림), 상호 참조가 어긋나는 원인이 그것이기 때문이다. 조 안의 문장이 갈라지는 드리프트는 이 테스트로 잡히지 않는다. 그것까지 잡으려면 대안 C가 필요하다.

조 표기의 흔들림도 관용한다 — `제14조(준거법)`처럼 공백 없이 쓰면 정규식에 걸리지 않아 그 조가 **검증 대상에서 조용히 사라지는** 문제가 있었다(783 QA M-1). 반각/전각 괄호와 전각 공백을 모두 받고, 조 개수 상수(`EXPECTED_ARTICLE_COUNT`)로 "양쪽이 동시에 마지막 조를 잃는" 형태까지 막는다.

### 5. 개인정보 처리방침은 이 결정의 대상이 아니다

`consent_terms`에 처리방침에 대응하는 `term_code`가 없다. 처리방침 자체는 `infra/nginx/html/legal/privacy/index.html`이 유일본이고, 앱은 그 페이지를 웹뷰로 연다. 다만 개별 절의 내용은 개인정보 관련 동의 6종의 문구와 같은 처리를 서술하므로, 그 동의 문구가 의미의 정본이다. 구조가 N:1이라 자동 대조 장치는 만들지 않았고, 상호 참조 주석으로만 연결했다.

## 결과 (Consequences)

**얻는 것**
- 앱 사용자가 동의하는 문구와 웹·스토어에 공표된 문구가 같아진다.
- 정적본의 사실 오류 3건이 해소된다.
- 조 번호·제목 드리프트가 CI에서 잡힌다(Docker 불필요). **단 §4의 Gradle 입력 선언이 살아 있을 때만 성립한다** — 선언 없이는 `infra/`만 바뀐 커밋에서 테스트가 실행되지 않는다(783 QA B-1 실측).

**감수하는 것**
- **개정 비용이 두 배다.** 문구 한 줄을 고쳐도 마이그레이션 추가와 nginx 이미지 재빌드가 모두 필요하고, 두 경로 모두 `develop` 병합 이후에만 반영된다(`Jenkinsfile`의 `Docker Build`는 `when { branch 'develop' }`).
- **조 안의 문장 드리프트는 여전히 사람이 막아야 한다.** 자동 감지 범위는 조 번호·제목까지다.
- DB 쪽 문구는 계속 `<p>`/`<br>`로만 쓴다. 기술적 필요가 아니라 대조 편의를 위한 제약이므로, 대안 C를 채택하면 함께 걷어낼 수 있다.

## 남은 미확정 (이 ADR이 정하지 않은 것)

- **`content_html` 갱신 시 소급 변경 위험.** `V29`가 `version='v1'` 행을 UPDATE했다. 그 시점에 `consent_records` 행이 있었다면 과거 동의 증빙의 문구가 소급으로 바뀐다. 운영 DB를 확인하지 못했다. 이후 개정은 §3의 절차를 따른다.
- **`effective_at = 2020-01-01`.** `V17`이 활성 조회(`isEffectiveAt(now)`)를 통과시키려 넣은 더미 값이다. 사용자에게 노출되면 명백한 오류지만, 노출 여부와 교정 방법은 확인하지 못했다.
- **DB본에는 "검토 중인 문서" 경고가 없다.** 정적본 머리말에는 있다. 즉 웹 방문자는 초안 경고를 보고 앱에서 실제 동의하는 사용자는 보지 못한다. `V29`를 고치지 않고는 해결할 수 없어 이번 범위에서 제외했다.
- **법무 검토.** 두 사본 모두 법무 검토 전 초안이다(`V29` 헤더 주석). 이 ADR은 "어느 쪽을 정본으로 볼 것인가"만 정하며 문구의 법적 타당성을 확정하지 않는다.
- **이 ADR 자체가 승인 대기다.** 머리말 참조. Jira 783 댓글의 "임의로 확정하지 않는다"와 이 문서가 아직 어긋나 있다.

### V30 마이그레이션에 묶여 있는 항목 (한 번에 처리해야 하는 것들)

아래는 전부 `content_html`을 바꿔야 해결되므로 **개별로 처리하면 안 된다.** 정적본만 고치면 이 ADR이 없애려는 드리프트를 그대로 재생산한다.

| 항목 | 내용 |
|---|---|
| 용어 통일 | 팀 용어 규칙은 "그림 심리 상담 리포트"이나 두 사본 모두 "관찰 리포트"를 쓴다(`V29:59,61,62,67,68`). 783에서 정적 `terms`의 사용 횟수가 3 → 4로 1건 늘었다(783 QA m-2). 정적본만 바꾸면 드리프트가 재발한다 |
| "검토 중인 문서" 경고 | DB본에 추가 (위 항목 참조) |
| `effective_at` 더미 | `2020-01-01` 교정 |
| `version` flip | 의미가 바뀌는 개정이면 새 `version` INSERT + 이전 버전 `is_active=FALSE` |

V30을 만들 때는 §3의 소급 변경 위험을 먼저 판단해야 한다(운영 DB에 `consent_records` 행이 있는지 확인 필요).
