# ADR-0001: 스트로크·대화 로그 저장소로 MongoDB 도입

> Jira: `S15P11B209-633` (본 문서) · 상세 설계는 `S15P11B209-368`(`docs/database/저장소-아키텍처.md`)
> 상태: **채택(Accepted)** — 2026-07-23 설계 확정, 본 문서는 2026-07-29 형식화
> 관련: 364(k8s 구성) · 365(BE 전환) · 369(MinIO, 같은 결정 축)

---

## 컨텍스트

두 가지 데이터가 관계형 스키마에 맞지 않는 형태로 쌓인다.

1. **스트로크(그리기 과정)** — 캔버스 획을 좌표 단위로 기록한다. 기존 설계(`stroke_batches`·
   `stroke_events`·`stroke_event_points`)는 **좌표 1개당 MySQL 1행**이다. 세션당 수만~10만 행이
   예상되고, 조회는 거의 항상 "세션 하나를 통째로 재생"이지 좌표 단위 조인이 아니다.
2. **대화 로그 원문** — AI 캐릭터와의 대화가 append-only로 고볼륨 누적된다. 스키마가
   유연해야 하고(질문 유형이 계속 늘어남), **보관 기간이 지나면 자동 삭제**되어야 한다
   (가드레일 9절 — 아동 데이터 수명주기).

이 두 스키마는 **아직 코드가 구현되지 않은 상태**(2026-07-23 기준 stroke_* 테이블은 빈 스펙만
존재)라, 저장소를 바꾸는 데 드는 비용이 지금이 가장 낮다. 나중에 실데이터가 쌓인 뒤 옮기면
이관 자체가 별도 프로젝트가 된다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| **MySQL 유지 (좌표=행)** | 세션 하나 재생에 수만 행 조인 — 인덱스 갱신 비용도 좌표 수에 비례해 쓰기 경로가 무거워진다. 조인이 필요 없는 데이터에 관계형 비용을 지불하는 구조 |
| **MySQL + JSON 컬럼** | 스키마 유연성은 얻지만 TTL(자동 만료) 기본 기능이 없다 — 삭제 배치 잡을 직접 만들어야 하고, 이는 가드레일이 요구하는 "보관 기간 경과 시 자동 삭제"를 사람이 만든 크론에 의존하게 만든다 |
| **MinIO(오브젝트)에 JSON 파일로 저장** | 파일 하나=문서 하나 방식은 되지만, "이 세션의 마지막 배치"처럼 부분 갱신·조회가 필요한 append 패턴에 맞지 않는다. MinIO는 이미 그림·음성 같은 불변 바이너리 몫으로 확정(369) — 역할을 겹치지 않게 분리한다 |
| **MongoDB** (채택) | 배치=문서로 임베딩하면 좌표당 인덱스 갱신이 사라진다(문서 1개 쓰기로 수렴). TTL 인덱스가 네이티브 기능이라 보관 기간 가드레일을 DB 레벨에서 강제할 수 있다. 스키마리스라 대화 로그의 필드 증가에도 마이그레이션이 없다 |

## 결정

스트로크(`strokes` 컬렉션)와 대화 로그 원문(`conversation_events` 컬렉션)을 MongoDB로 옮긴다.
관계형 핵심(사용자·아동·동의·세션/분석 메타)은 **MySQL에 그대로 둔다** — FK 무결성과
트랜잭션이 필요한 데이터에만 관계형 비용을 지불한다.

문서 설계 원칙(상세는 `저장소-아키텍처.md` §5):
- **배치=문서, 좌표=문서 아님** — `{ sessionId, batchSeq, strokes: [...], expireAt }`.
  포인트 하나마다 문서를 만들면 MongoDB에서도 같은 문제(문서 수 폭증)가 재현된다.
- **TTL 인덱스로 보관 기간을 코드가 아니라 DB가 강제** — `expireAt` 필드 하나로 만료를 표현하고,
  동의 철회·회원 탈퇴는 TTL을 기다리지 않고 `deleteMany({childId})`를 즉시 실행한다.
- **인증 필수** — MinIO와 동일 원칙(root 관리 계정 + 앱 전용 최소권한 계정 분리), ClusterIP 전용,
  시크릿은 `sync-secrets.sh` 체계에 편입한다. 무인증 MongoDB를 열어두지 않는다.

## 결과 (Consequences)

**얻는 것**
- 스트로크 쓰기 경로가 좌표 수에 무관하게 배치 단위로 수렴 — 인덱스 갱신 비용 대폭 감소
- 보관 기간·삭제가 TTL 인덱스로 구조적으로 보장됨 (가드레일 9절 요구사항과 직접 정합)
- 대화 로그 스키마 변경이 마이그레이션 없이 가능

**감수하는 것**
- 저장소 종류가 하나 늘어난다 (MySQL + Redis + MinIO + MongoDB) — 폴리글랏 퍼시스턴스의
  운영 부담(백업 체계·모니터링·장애 대응 절차를 하나 더 만들어야 함)이 생긴다.
  → 대응: 백업은 353(MySQL 백업)과 동일 취급 규정(mongodump CronJob)으로 통일해 별도
  운영 방식을 만들지 않는다.
- `conversation_events`를 Mongo 단일 소스로 할지 MySQL `conversation_messages`를 유지할지는
  **아직 미확정**(365에서 BE와 협의) — `audio_variants` 외래키 제약 때문에 완전히 자명하지 않다.
  **확정 전까지 두 곳에 동시 저장(이중 저장)은 금지** — 어느 쪽이 진실인지 모호해지는 상태를
  만들지 않는다.
- 기존 `stroke_batches`·`stroke_events`·`stroke_event_points` 스키마는 코드가 없으므로
  데이터 이관이 아니라 **스키마 v1.3 개정에서 제거**한다(ERD 갱신 필요).

## 실행 순서 (착수 조건)

364(MongoDB k8s 구성)는 **k3s 컷오버(360) 이후**로 잡혀 있다(3차 실행 로드맵, 07/30~31).
compose 단계에 별도 MongoDB 컨테이너를 먼저 얹지 않는 이유: 이 스택은 이미 컨테이너 11개가
15.6GB RAM을 나눠 쓰는 상태([[메모리-OOM-대응]] 참조)라, k3s가 자원을 재조정하기 전에
서비스를 하나 더 얹으면 예산을 벗어난다. 설계는 지금 확정하되 **적용은 k3s 위에서** 한다.
