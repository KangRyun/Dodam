## 3. 스트레스 결과 — 읽기 경로 한계 탐색

02 인증 조회를 계단식으로 VU 상승(각 단계 15~25s 램프 + 20~45s 유지). 읽기라 데이터 누적 없음.

| VU | throughput | read p95 | read max | 실패율 |
|---:|---:|---:|---:|---:|
| 50 | 238 rps | 29ms | 169ms | 0% |
| 100 | 368 rps | 206ms | 921ms | 0% |
| 200 | 448 rps | 567ms | 1,506ms | 0% |
| 400 | 493 rps | 1,119ms | 3,383ms | 0% |
| 800 | **524 rps** ← 정점 | 2,071ms | 5,036ms | 0% |
| 1600 | **398 rps** ↓ | 5,077ms | 9,603ms | 0% |

> 3200 VU 는 공유 운영 인프라 과부하 우려로 실행하지 않음(안전 정책 차단 + 실사용자 영향).
> ⚠️ **1600VU 행은 다른 빌드**(측정 사이 배포 발생, 6절 단서①) — 800VU 와 엄밀 동일조건 아님.

### 해석

- **처리량 정점 ≈ 520 reqs/s @ 800 VU.** 그 위(1600 VU)에선 오히려 398 rps로 **역행** — 컨텍스트 스위칭·큐 스래싱에 의한 **혼잡 붕괴(congestion collapse)** 구간 진입.
- **지연 SLO(read p95<400ms) 붕괴점 ≈ 150 VU.** 100VU(206ms)까지 여유, 200VU(567ms)에서 초과.
- **에러 벽은 1600 VU 까지도 없음.** 5xx·타임아웃·커넥션 드롭 0건. 서버가 전부 큐잉해 **끝내 응답** — 연쇄 실패 없이 지연으로만 흡수하는 **우아한 성능 저하(graceful degradation)**.

### 결론 — 용량 가이드

| 지표 | 값 |
|---|---|
| 실용 동시성 한계 (p95<400ms) | **≈ 150 VU** |
| 최대 처리량 (읽기 경로) | **≈ 520 reqs/s** |
| 혼잡 붕괴 시작 | 800 VU 초과 |
| 에러(실패) 발생 | 1600 VU 까지 **없음** |
| **정점 병목** | **HikariCP 커넥션풀 기본값 10 고갈** (CPU 아님 — 6절) |

읽기 경로는 부하가 몰려도 죽지 않고 느려질 뿐이며, backend 2-레플리카 + K8s Service 로드밸런싱이 폭주 상황에서도 견고함을 보인다. 용량 증설이 필요한 신호는 "실패"가 아니라 **p95 지연 상승(≈150 VU 이상)** 으로 판단해야 한다. **정점(~520 rps)의 근본 원인은 CPU가 아니라 커넥션풀 크기 10**이며(6절 참조, CPU는 limit의 20~43%로 여유), 풀을 20~30으로 올리면 같은 하드웨어에서 처리량 상향 여지가 크다. 이것이 이번 측정의 핵심 실행 항목이다.

## 4. 측정 중 발견·수정한 이슈

측정 준비/실행 과정에서 k6 도구가 현행 백엔드 계약과 어긋난 3건을 발견해 고쳤다.

1. **`02-authed-read.js` — `/api/v1/drawing-types` 필수 파라미터 누락.**
   `childId`(`@RequestParam @Positive`)를 안 붙여 400(`COMMON_400_004`). `?childId=${childId}` 추가.
2. **`03-drawing-upload.js` — 같은 `drawing-types` 400 + 응답 구조 불일치.**
   `setup()` 이 `childId` 없이 호출 → 400 으로 시나리오 전체 abort. 또한 목록은 페이지 응답의
   `data.content` 인데 `data.drawingTypes` 로 읽고 있었음. `CHILD_IDS[0]` 로 조회 + `content` 로 수정.
3. **`make-png.mjs` — 이미지 픽셀 크기 미달(422).**
   합성 PNG 가 180×189 인데 백엔드 `ImageDimensionPolicy` 는 가로·세로 **모두 320~8192px** 만 허용
   (`STORAGE_422_001`). 320px 하한을 깔아 기본 산출물을 **320×320(≈300KB)** 로 변경.

> README 의 "2026-07-30 사전 확인"은 무인증 401 경계만 봐서 위 인증·업로드 계약 불일치를 놓쳤다.
> 다음 측정 전 사전 점검 항목에 **인증 포함 스모크 1회**를 추가할 것.

## 6. 서버 리소스 (측정 창) — Prometheus

backend limit: **CPU 2코어 / mem 1536Mi** (requests 250m / 768Mi). 파드 2개(replica).

| 구간 | 부하 | 피크 CPU(코어)/파드 | limit 대비 | 피크 mem(MiB)/파드 | 재시작 |
|---|---|---|---|---|---|
| 정상 | 30VU | 0.403 / 0.384 | 20% / 19% | 517 / 482 (34%/31%) | 0 |
| 스트레스 | 800VU | 0.589 / 0.569 | 29% / 28% | 629 / 676 (41%/44%) | 0 |
| 폭주 | 1600VU | 0.859 / 0.803 | 43% / 40% | 628 / 685 (41%/45%) | 0 |

- **로드밸런싱 균등.** 세 창 모두 두 파드 CPU가 3~7% 이내로 붙음(예: 1600VU 0.859/0.803). 메모리도 동일 수준, 쏠림 없음 → K8s Service 분산이 실제로 고르게 동작.
- **재시작·OOM 0건.** 메모리는 최대 limit의 45%로 여유 큼.

### ★ 정점 병목 = CPU 포화가 아니라 HikariCP 커넥션풀(기본값 10) 고갈

| 지표 | 30VU | 800VU | 1600VU |
|---|---|---|---|
| hikari 풀 크기 | 10 | 10 | 10 |
| hikari pending(대기 스레드) | 0 | 190 | 191 |
| acquire 최대 대기 | 0.002s | 3.945s | 8.078s |
| in-flight HTTP 요청 | 2 | 200 | 200 |
| jvm live threads | 45 | 239 | 237 |
| HTTP 최대 지연 | 0.035s | 3.962s | 8.162s |

- **CFS 스로틀링 사실상 0**(최대 0.28%, 순간). CPU limit에 붙은 적 없음 → "CPU 포화 아님"의 결정적 증거.
- **in-flight가 정확히 200에서 천장** = Tomcat `max-threads` 기본값. 그 200개 중 **190개가 커넥션 대기로 blocked**.
- **HTTP 최대 지연 ≈ acquire 대기**(3.96s≈3.95s, 8.16s≈8.08s) — 요청 시간의 대부분이 실제 작업이 아니라 **풀 대기**.
- `application.yml`에 hikari·tomcat 설정 없음 → Spring Boot 기본값(풀 10, 스레드 200). 관측된 천장과 정확히 일치.
- 800→1600VU에서 대기 3.9s→8.1s로 2배, 처리량은 520→398rps로 하락 → 풀 상한 고정 상태에서 VU만 늘어 **큐만 깊어지는 무릎점 이후 붕괴**.
- acquire **타임아웃(기본 30s) 실패 0건** → 대기는 했으나 획득 실패로 떨어진 요청은 없음(그래서 실패율 0%).

**조치 방향**: HikariCP 풀 **10 → 20~30** (단, MySQL `max_connections` 와 `2파드 × 풀크기` 동시 점유 확인 필수). Tomcat 스레드 200은 유지 — 늘리면 대기열만 깊어짐.

### 측정 신뢰도 단서 (서버 CC 교차검증)

1. **⚠️ 폭주(1600VU) 창은 다른 빌드다.** 정상·스트레스는 `backend-58ddd94c-*`(이미지 24a74fbc), 폭주는 `backend-cfd79d786-*`(이미지 ad8c03b3) — 두 테스트 사이에 배포가 끼었다. **1600VU 값은 800VU와 엄밀히 동일 조건 비교가 아님**(병목 원인=풀 고갈 결론 자체는 두 빌드 공통이라 유효).
2. **Hikari/JVM 지표는 파드별 분리 안 됨.** 스크레이프 타깃이 `backend:9404`(Service DNS) 단일이라 매번 두 파드 중 하나가 임의 응답 → 위 pending 190·in-flight 200은 **한 파드 값, 클러스터 합계는 대략 2배**. 파드 단위 디스커버리로 전환 필요(모니터링 갭).
3. **교차검증 OK.** 파드별 http_rps 피크 275.8 × 2파드 ≈ **551 rps** 로 k6 측정 ~520 rps 와 일치.
