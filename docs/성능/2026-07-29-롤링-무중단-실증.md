### 왜 클러스터 안에서 돌리나

**호스트에서 NodePort 로 치면 안 된다.** 이 호스트에서는 k3s 를 완전히 정지시켜도
30080 → 301, 30443 → 200 이 나온다(운영 nginx 가 응답). 스테이징을 잰다고 믿으면서
운영을 재게 된다. 클러스터 안에서 Service 를 직접 치면 모호함이 없다.

### 왜 `/api/v1/children` 하나만 치나

- `/` 랜딩은 nginx 가 정적으로 돌려준다 → 백엔드가 죽어도 200 이다. 무중단을 증명하지 못한다
- `/ai/health` 는 스테이징에서 ai 가 replicas 0 이라 502 다(의도된 구성)
- 무토큰 401 이 끊기지 않는 것 = "게이트웨이 → 백엔드 → 인증 필터"가 살아 있다는 뜻

401 은 `expecting(401)` 로 성공으로 세게 했다. 남는 실패는 502·503·타임아웃뿐이고,
그게 정확히 잡고 싶은 것이다.

## 원인 — `maxUnavailable: 0` 만으로는 부족하다

`backend.yaml` 의 롤링 설정은 처음부터 옳았다.

```
maxSurge: 1 · maxUnavailable: 0        ← 용량은 보장된다
terminationGracePeriodSeconds: 30
preStop                                 ← 없었다
```

파드가 삭제되면 두 가지가 **순서 보장 없이 동시에** 일어난다.

1. kubelet 이 SIGTERM → 앱이 종료 시작
2. 엔드포인트 컨트롤러가 Service 에서 제거 → kube-proxy 가 iptables 갱신

①이 먼저 끝나면 **아직 라우팅이 살아 있는 채로 앱이 죽는다.** 그리로 간 요청은 응답을
받지 못하고, nginx 의 `proxy_read_timeout` 이 120s 라 그때까지 버틴다. 사용자에게는
에러 페이지가 아니라 **멈춘 화면**으로 보인다 — 에러보다 나쁘다.

`maxUnavailable: 0` 은 "몇 개가 살아 있는가"를 보장할 뿐 이 경쟁을 막지 못한다.
주석에 "무중단의 근거"라고 적혀 있었지만, 실측해 보니 절반만 맞는 말이었다.

### 해법

```yaml
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 8"] }
```

엔드포인트 제거가 전파되는 동안 계속 서빙하고, 그 뒤에 SIGTERM 을 받는다.
8초인 이유: 전파는 보통 1~2초면 끝난다. 4배 여유를 두되 `terminationGracePeriodSeconds`(30)
안에 충분히 들어가는 값이다. ⚠️ 이 값이 grace period 를 넘으면 preStop 도중 SIGKILL 되어
역효과가 난다.

## 측정 중 걸렸던 함정 2가지 (재현할 사람을 위해)

**① TLS 인증서 이름 불일치** — 첫 실행에서 1790건 전부 실패했다. `http://gateway` 로 쳤더니
게이트웨이가 https 로 301 을 주고, 그 인증서는 공개 도메인용이라 Service 이름과 맞지 않았다.
결과는 "무중단 실패"처럼 보였지만 실제로는 **백엔드까지 가보지도 못한** 것이었다.
→ 시나리오에 `insecureSkipTLSVerify: true`. 클러스터 안에서는 구조적으로 통과할 수 없다.

**② 리다이렉트가 지표를 오염시킨다** — `http://` 로 주면 반복당 2요청(301 + 본요청)이 되고,
301 이 `expecting(401)` 과 어긋나 실패로 잡힌다. `http_req_failed` 는 50% 인데 체크 성공률은
99.4% 인, **지표 두 개가 서로 다른 말을 하는** 상태가 된다.
→ `BASE_URL` 은 반드시 `https://gateway`.

## 2026-07-31 운영 재확인 (S15P11B209-362)

> 위 실증은 스테이징이었다. 360 컷오버 후 **운영(prod)에서 backend 롤링이 무중단인지** 다시 확인했다.
> 결론: **무중단 통과.** 롤링 드레이닝 순간에 실제 요청이 흘렀고 실패 0.

### 방법 (스테이징과 다른 점 — 운영은 외부에서)

```
시나리오  05-rolling-smoke.js (무토큰 → 401 이 정답, 502/503 만 실패로 잡힘)
부하      5 VU × 5m (constant-vus), 외부 노트북 → 공개 도메인 https://i15b209.p.ssafy.io
롤링      k6 창 중앙에서 서버가 kubectl -n dodam rollout restart deployment/backend
판정      http_req_failed rate == 0 + 롤링 드레이닝 구간과 요청별 로그 시각 대조
```

스테이징은 "클러스터 안 http://gateway" 로 쳤지만(NodePort 로 치면 운영 nginx 를 재는 함정),
운영 검증은 **공개 도메인을 외부에서** 치는 게 맞다 — 실제 사용자 경로와 같다.

### 결과 — 시각 대조로 검증

배포 설정 확인: `preStop=sleep 8` · `maxSurge=1` · `maxUnavailable=0` · `grace=30` (스테이징과 동일).
롤링: 14:11:29 시작 → 14:12:36 완료(67초). **Ready 파드는 롤링 내내 최소 2**(0으로 떨어진 순간 없음).

| 구간 | 요청 | 실패 |
| --- | --- | --- |
| 전체 (5m) | 2,923 (전량 401) | **0** |
| 롤링 구간 14:11:29~14:12:47 | 750 | **0** |
| └ 구 파드#1 드레이닝 14:12:02~11 | 85 | **0** |
| └ 구 파드#2 드레이닝 14:12:36~47 | 105 | **0** |

핵심은 **두 파드가 죽는 순간에 실제로 190개 요청이 흘렀고 전부 401(백엔드 도달)로 성공**했다는 것이다.
preStop 8초가 엔드포인트 제거 전파 동안 in-flight 를 받아낸다는 스테이징의 결론이 운영에서 재현됐다.

### 정직하게 남기는 이상치 — 1차 시도 11% 실패

같은 날 첫 시도에서는 http_req_failed 11.08%(326/2940, 전부 빠른 502/503)가 나왔다. 그러나 그 시도는
**롤링 트리거 시각 보고가 없어 실패와 롤링의 상관관계를 맞추지 못했다.** 3차(위)는 드레이닝 구간까지
요청별로 대조해 깨끗했으므로, 1차 11% 는 (a) 롤링과 무관한 순간 이벤트, (b) 게이트웨이성 순간 장애,
(c) 오랜만의 첫 재시작 이미지 pull 지연 중 하나로 추정되나 **데이터 부족으로 단정하지 않는다.**
운영에서 롤링을 자주 돌릴 때 재현되는지 관찰 대상으로 남긴다.

### 함정 하나 더 (외부→운영 재현 시)

이 시나리오는 원래 클러스터 안 실행용이라 `insecureSkipTLSVerify: true` 다. 외부에서 공개 도메인
(유효 인증서)으로 칠 때는 무해하지만, **롤링 트리거가 k6 창 안에 확실히 들어오게** 해야 한다.
1차·2차가 흔들린 것도 창-롤링 겹침이 불확실해서였다. 3차처럼 **서버가 롤링 epoch 를 보고 → 외부가
요청별 로그와 대조**하는 방식이라야 "못 봤다"와 "없었다"를 구분할 수 있다.
